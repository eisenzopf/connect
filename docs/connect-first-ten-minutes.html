01

Your assistant becomes reachable.

Connect gives a person, app, or agent a communications identity. An assistant can ask you a question—and you can start a conversation with it yourself.

Start Connect, connect your Vapi assistant and Telnyx account, and give your assistant a place where people, apps, and other agents can reach it.

Identity

A stable place to reach.

One participant identity with configured addresses and routes: a native Connect address, a telephone number, and access from apps and browsers.

Capability

A clear way to participate.

Discover whether a route supports messages, files, voice, or video, and whether the caller is allowed to use it.

Continuity

A conversation with context.

Keep exchanges and live sessions related. Deliver a reply to the right conversation and, where supported, the assistant task waiting for it.

Presence here means addressability, supported capabilities, permissions, and a delivery path. Availability is a separate state: an identity can exist while its assistant is disconnected. Connect provides communication; the configured assistant provides reasoning.

02

From keys to a conversation.

The target: a developer can reach their assistant, hear back, and watch the assistant reach out—all from one running Connect server.

Bring your accounts

Vapi + Telnyx.

Bring account credentials, select a Vapi assistant and a Telnyx number enabled for the paths you want to test, and provide an approved human contact. The setup flow should explain and help complete missing configuration.

Try locally first

No provider account required.

A bundled local example connects two participants through the native SDK. Exchange a message and a file before connecting services. This also gives contributors a repeatable development path.

“Ten minutes” is a usability target for a supported machine and ready provider accounts, measured after installing the server package. Number provisioning, carrier approval, and public endpoint setup may take longer. The server must show those prerequisites clearly; this is not a measured claim.

  1. 00–02 min
    Start

    Run one server.

    Install the published server package for a supported platform, then start its interactive setup. The package name and distribution formats will be chosen after the reuse audit.

    Proposed terminal experienceNot executable yet
    connect init
connect serve

Connect is running.
Native UCTP / QUIC: ready on loopback
Local state: persistent
Provider routes: not configured

Next: connect setup

    Success: the server reports its endpoint, local state location, and health. Restarting it preserves the installation identity. Setup and diagnostics connect to this same process.

  2. 02–04 min
    Connect

    Add the two keys. Choose what they connect.

    The setup command reads secrets through hidden prompts and stores them in the configured secret store. It lists available resources and lets the developer choose an assistant and number.

    Proposed setup promptsCredentials stay on the server
    connect setup

Vapi API key:             [hidden input]
Vapi assistant:           [choose existing / configure one]
Telnyx API key:           [hidden input]
Telnyx number:            [choose an eligible number]
Public callback origin:  [configured deployment URL]
Human test contact:      [your verified contact]

Review proposed routing changes → Apply → Check readiness

    Show the exact number, assistant, callback, messaging, and voice changes before applying them. Reuse compatible configuration; make any replacement of an existing route explicit. Verify the selected human contact using a defined ownership check before treating it as trusted.

    Success: each route shows ready, needs configuration, or unavailable, with a specific next action. A valid API key alone never marks an untested route ready.

    What setup should handle

    Discover resources; explain number capabilities; configure or reuse messaging and voice resources; establish callback verification and endpoint reachability; select an explicit Telnyx/SIP/Vapi routing topology; and perform authorized test exchanges. Require confirmation before a test incurs provider charges. A local-only installation can run the native demo while external routing remains pending. Public ingress and NAT traversal are design decisions to resolve, not an assumed hosted Connect service.

  3. 04–06 min
    Give presence

    Name the assistant and make its routes visible.

    Bind the selected Vapi assistant to a Connect identity. Associate the selected telephone number with it, and authorize the human test contact. Native apps use the identity; people can use the configured number.

    Proposed identity summaryIllustrative address syntax
    connect presence create assistant --integration vapi
connect presence show assistant

Identity:    assistant
Address:     connect:assistant@local
Assistant:   [selected Vapi assistant]
SMS:         [selected Telnyx number] — ready
Voice:       [selected Telnyx number] — ready
Native:      messages — ready
Access:      approved contacts and scoped clients

    Success: another authenticated local client can resolve this identity and inspect its permitted routes. “Local” is a server-local namespace, not a globally resolvable address. Remote clients need an explicit server endpoint and credential.

  4. 06–08 min
    Reach it

    Text your assistant. Then talk to it.

    From the approved human phone, send a message to the configured number. Connect routes it to the Vapi assistant and returns its answer through Telnyx. Call the number to test the configured voice route.

    • Human · SMS“I’m comparing option A and option B. Help me choose.”
    • Assistant · SMS“What matters most: cost or speed?”
    • Human · SMS“Speed. I’ll call to talk it through.”

    The phone’s SMS thread does not carry a Connect task ID. The first-run policy keeps one active conversation for this approved contact and assistant. Cross-channel continuation requires that explicit binding; ambiguous or unverified callers start a separate conversation. The Vapi integration must map chat and call context deliberately.

    Success: a real incoming SMS gets a real answer, and a real call exchanges audio in both directions. Logs show the Connect conversation and provider leg IDs. A correlated call record alone does not prove the assistant received prior context.

  5. 08–10 min
    Let it reach back

    The assistant uses Connect, too.

    During the call, ask the assistant to send you a summary and a follow-up question. With the configured permission, it uses a Connect MCP tool to send an SMS. Reply from your phone.

    • Human · Voice“Text me the summary and ask which option I want.”
    • Assistant · Connect toolsend_message → approved human · current conversation
    • Human · SMS“Go with B.”
    • Assistant · SMS“B it is. I’ve recorded your choice.”

    The new reply is delivered through the Vapi integration. Continuing a separate background job needs an explicit host/task binding; an ended call is not assumed to remain an executing task.

    Success: the assistant is both reachable and able to reach out. Its tool action, provider acceptance, delivery outcome when available, and incoming reply are distinguishable in the same conversation.

The moment that should feel different: you can reach your assistant using your phone, an app can reach the same identity using the SDK, and the assistant can use Connect to contact you. Each participant uses an interface appropriate to it.

03

A developer should see the whole loop.

Connect, resolve, send, receive. The SDK should make incoming communication as approachable as outgoing communication.

TypeScript-shaped pseudocode illustrates the intended server-side SDK experience. The implemented foundation is the Rust SDK; Gate 2 adds TypeScript and Python via a persistent Rust QUIC helper, with a separate local HTTP/JSON option. The examples below remain product sketches; see SDK.md for actual methods. Browser media is qualified separately in Gate 3.

Proposed SDK · initiate and receivePseudocode
const client = await Connect.open({
  endpoint: config.server,
  credential: secrets.appCredential, // scoped Connect credential
  transport: "uctp-quic"
});

const assistant = await client.resolve("connect:assistant@local");
assistant.require("messages");

const conversation = await client.conversations.create({
  participants: [assistant.id],
  requestId: saved.createRequestId
});

await conversation.messages.send({
  text: "Help me compare these two options.",
  requestId: saved.sendRequestId
});

for await (const event of client.events.resume(saved.cursor)) {
  if (event.type === "message.received" &&
      event.conversationId === conversation.id) {
    await app.applyOnce(event.id, event); // include deduplication
  }
  await checkpoints.save(event.cursor);
}

Persist operation IDs before sending and reuse them on retry. Event handling must tolerate redelivery; a durable cursor alone does not make application side effects exactly once. Provider credentials never appear in the application client.

Make your own app or agent reachable

The same client can bind an identity it is authorized to serve, subscribe to its inbox, and reply inside an incoming conversation. Stable identity registration and the runtime consumer subscription have separate lifecycles.

Proposed SDK · an incoming conversationPseudocode
const inbox = await client.presences.bind({
  identity: "reviewer",
  capabilities: ["messages"]
});

for await (const event of inbox.events.resume(saved.cursor)) {
  if (event.type === "message.received") {
    await jobs.enqueueOnce(event.id, {
      conversationId: event.conversationId,
      message: event.message
    });
  }
  await checkpoints.save(event.cursor);
}

// A durable worker processes the job and replies using
// the same conversationId and a saved requestId.

Binding an identity does not make it publicly accessible. Server permissions govern who may discover it and initiate conversations. Retry safety at a provider boundary must be qualified separately.

Files

Share an artifact with its audience.

The SDK sends a file reference with explicit access and attaches it to a conversation. An SMS route may need a permitted link rather than a native attachment; unsupported delivery must be reported.

Voice + video

Invite, accept, participate.

A session invitation requests supported media and returns a session ID. Media flows through the runtime’s negotiated transport. The reference client exercises messages, files, voice, and video through the public interfaces.

04

An agent should be able to pick it up.

Install the tools, give the agent a scoped identity, and teach one useful workflow. Prove the reply reaches the task that needs it.

Vapi · Required

Use Connect while talking.

Configure the assistant to consume the Connect MCP endpoint using scoped credentials. Expose only the permitted operations. Bind each invocation to its authenticated assistant and mapped call/chat conversation.

Additional assistant · Required

Install and continue a task.

Select one host after evaluating Meta Muse, Grokbot, OpenClaw, Codex, and other candidates. Verify the exact product, installation path, and incoming event behavior. Support is unconfirmed until demonstrated.

Proposed installer experienceHost selected through research
connect agent install --host <selected-host>

Connect identity:   reviewer
Credential:        scoped to approved contacts and conversations
MCP tools:         installed
Connect skill:     installed where the host supports skills
Reply delivery:    [host adapter / bounded wait / explicit resume]
Verification:      send → receive → continue

The installer should expose the host’s actual delivery mode. A skill teaches workflows; it does not grant authority. MCP supplies operations; it does not guarantee that a suspended assistant can wake itself.

Agent’s intentionProposed toolWhat the result must tell it
Find the right recipientresolve(address)Stable participant ID, permitted routes, capabilities, and availability where known.
Ask or respondsend_message(to, text, request_id, conversation_id?)Request, message, and conversation IDs; accepted, rejected, or unknown outcome.
Share the draftsend_file(conversation_id, artifact_id, request_id)Access scope and the selected route’s supported delivery form. No arbitrary local filesystem access is implied.
Receive the answerwait_for_events(cursor, timeout, conversation_id?)Correlated events and a resume cursor, or an explicit timeout. Host adapter delivery is another supported path.
Recover contextread_conversation(conversation_id)Authorized history, participant identities, and operation outcomes.
Talk it throughstart_session(conversation_id, media, request_id)Invitation/session state and how a media-capable runtime joins. Audio packets are not tool arguments.

The first skill workflow: “Send my human this draft, ask which option they prefer, and continue when they reply.” Resolve the approved human, check the route, share the artifact, send the question, save the conversation-to-task binding, and receive the answer through the documented host delivery mode. On resumption, recover the original task and apply its existing authority.

An incoming message is communication, not automatic permission to execute its instructions. Provider event IDs and phone numbers aid correlation; they are not substitutes for authentication and authorization.

05

Journey two · For application developers

Make your app reachable.

Give your app a Connect identity. Let people, agents, and other apps start a conversation with it—and let your app reach back through the same interface.

Your app can tell someone what happened, ask what to do next, and receive the answer. Others can also reach it first.

The developer brings

An app and its behavior.

The app owns its users, records, and business logic. Its Connect integration decides which requests it understands, maps conversations to application records, and checks permission before taking action.

Connect supplies

A shared communication surface.

The server and SDK provide identity, permitted routes, conversations, incoming events, and outgoing communication. Add provider connectors when the app needs telephone or messaging networks.

This is a second entry point into the same v0.1 product. A native app-to-app exchange needs no Vapi or Telnyx account. Vapi is useful when the app wants a voice or conversational assistant; Telnyx adds configured phone and SMS routes.

Example: a review app that can ask—and be asked.

A review app manages drafts and approval decisions. It can ask its human to review a draft. A person or authorized agent can also contact the app to ask which drafts are waiting.

  1. 01
    Identify

    Give the app an address.

    Register connect:reviews@local, issue a scoped application credential, and bind its inbox through the SDK. Publish supported communication capabilities and a small description of what the app understands. Grant access to selected users and clients.

    Success: a separate authorized client can resolve the app and discover that it accepts messages. Unauthorized clients cannot read its conversations.

  2. 02
    Reach out

    Ask a human to review something.

    When a draft is ready, the app creates a conversation with the assigned reviewer, shares the permitted artifact, and asks a specific question. The app stores the mapping from its review record to the Connect conversation.

    • Review app → Human“Draft 42 is ready. Should we use option A or B?”
    • Human → Review app“B.”
    • Review app → Human“Recorded B for draft 42.”

    Success: the reply reaches the right review record. The app checks that the sender is an authorized reviewer before recording the decision. A delivered notification by itself is not completion.

  3. 03
    Be reached

    Let someone else start.

    A person in the reference client or a separately written agent resolves the app and initiates a new conversation. The app's inbox receives it without a prior outgoing notification.

    • Authorized agent → Review app“Which drafts are waiting for my human?”
    • Review app → Authorized agent“Draft 42 is waiting. Here is the permitted review link.”

    The example app can use a small set of documented commands such as pending and review 42. Natural-language understanding is optional application behavior, not an automatic Connect feature. Acting on behalf of a human requires an explicit authorization mapping.

    Success: the app receives and answers an independently initiated request. An unrecognized request returns a helpful explanation of supported requests.

  4. 04
    Extend

    Reach the app from another channel.

    Attach a configured Telnyx SMS route to the same app identity and let an approved human contact it from their phone. Add a Vapi assistant when a conversational voice interface would help; expose only the app operations that assistant is allowed to invoke.

    Success: the developer reuses the same conversation handling and application rules. The connector exposes channel limits, identity assurance, and any ambiguity rather than hiding them.

  5. 05
    Recover

    Keep the app reachable across restarts.

    Restart the app worker, resume its inbox from a saved cursor, and process queued work without recording the same decision twice. The server retains the identity and accepted messages according to its delivery and retention policy.

    Success: the app catches up on durable events, returns responses to the original conversations, and clearly reports expired or failed work.

Proposed application handler: connect communication to existing logic

This builds on the SDK inbox example above. The app owns authorization and review semantics. The durable worker persists its work and response ID so retrying the handler does not repeat the business action.

Proposed app workerPseudocode
async function handleReviewMessage(job) {
  const actor = await users.mapConnectParticipant(job.senderId);
  await reviews.authorize(actor, job.reviewId);

  const result = await reviews.applyOnce(job.eventId, {
    actor,
    reviewId: job.reviewId,
    request: job.message
  });

  await client.conversations.get(job.conversationId).messages.send({
    text: result.reply,
    requestId: job.savedResponseId
  });
}

The application obtains the review ID from its validated conversation mapping or a validated incoming request. It does not trust an arbitrary message to select records or authorize changes. An unknown delivery result requires reconciliation before another external send.

One foundation, two journeys. “Give an agent presence” starts with an existing assistant. “Make your app reachable” starts with your application's own logic. Both use the same identities, conversations, capabilities, permissions, and delivery model. Neither requires a later release or a separate communications stack.

The app journey fits the existing gates: native reachability in Gate 1, SDK chat and telephone participation in Gate 2 (live SMS deferred), native media in Gate 3, and distribution/recovery checks in Gate 5. A general app marketplace or universal business-action protocol is not required to demonstrate it.

06

One interface that reaches outward.

UCTP supplies the shared communication model. QUIC is the native connection. Connectors translate at the boundary so existing services can participate.

Native proof

Control and live media.

Independent client and server processes exchange reliable UCTP control over QUIC streams and live media over QUIC datagrams. A message-only demo does not prove the media path.

Provider boundary

Keep the external world usable.

The Vapi connector uses its supported chat and voice interfaces. Telnyx supplies configured telephone and SMS routes. Native QUIC does not change an external provider’s WebSocket or SIP transport guarantees.

An independently written client should be able to reach a permitted identity using the published UCTP profile. Independent implementation, negotiation, addressing, and conformance evidence belong in the roadmap alongside the SDK experience.

07

Make the next action obvious.

Good setup includes clear failure states. A new user should know which part needs attention without understanding every provider’s signaling model.

SituationWhat Connect should sayExpected behavior
Key rejected“Vapi authentication failed. Update the stored credential.”Keep the local server and other working routes available; never echo the secret.
SMS not ready“This number cannot send SMS yet. Complete the listed provider requirements.”Identify capability, configuration, or account readiness as the cause; do not claim a delivery attempt succeeded.
Callback unreachable“Incoming messages cannot reach this server. Verify this callback URL.”Show inbound and outbound readiness separately and provide a repeatable diagnostic.
Assistant unavailable“The assistant is disconnected. Your message is queued.”Say “queued” only after durable acceptance. Show expiry and delivery policy; otherwise return an explicit failure.
Provider result uncertain“The request may have reached the provider. Delivery is unknown.”Reconcile if possible. Do not blindly retry a billable operation that could be duplicated.
Reply is ambiguous“More than one conversation could match this reply.”Use the published routing policy or request clarification; never guess which task should continue.
Connection interrupted“Reconnected. Resuming events from the saved cursor.”Deduplicate durable events. Report live session interruption separately; live audio is not replayed.
08

Build toward visible proof.

The walkthrough is a target experience. The roadmap should deliver parts of it that people can run and evaluate along the way.

These are proposed outcomes, not scheduled commitments. They retain the full v0.1 scope in the contract. The reuse audit and experiments may change task ordering and reveal parallel work.

What we should review in this experience.

  • Does “presence” explain the two-way value clearly?
  • Can a developer tell what the server, SDK, and assistant each do?
  • Are keys, resource selection, and route readiness understandable?
  • Can a person, agent, or another app initiate a permitted conversation with the assistant or app?
  • Can an assistant use its tools, and an app use its SDK, to reach a human and receive a reply?
  • Is reply handling explicit enough to avoid continuing the wrong task?
