B-001 · Identity, reachability, presence and preferences

Broader registry decision open · Basic availability qualified in Gate 3 · Product owner: maintainer · Review before closing the v0.1 scope.

One registered person, app or agent. Multiple ways to communicate. Availability and preferences that can change over time.

The original Gate 1 design mentions runtime availability, while its accepted messaging contract implements durable identity and inbox reachability. That mismatch remains visible. The broader user-managed endpoint registry and preference system discussed here is a proposal awaiting a scope decision, not an implemented feature or an automatic expansion of Gate 1.

What users could do

Manage how they can be reached.

Register SMS, telephone, browser and native Connect endpoints against one stable identity. Set preferences such as “prefer SMS today” or “no calls until 5,” and make a temporary override expire automatically.

The same model should work for an app or AI assistant. A persistent inbox may remain reachable while its runtime is offline.

Four distinct facts

A reachable endpoint is not consent to interrupt.

  • Identity: who the participant is.
  • Capabilities and endpoints: which communication methods exist.
  • Availability: what is known about current reachability, with freshness.
  • Preferences: which permitted methods the owner wants used.

Decisions to make

Preserve the required capability while deciding the smallest useful implementation.

  1. Release scope: assign the original availability requirement to a delivery gate; decide which registry and preference features belong in v0.1.
  2. Ownership: decide which registration/presence primitives belong upstream in rvoip/UCTP and which durable records, schedules and routing policy belong in Connect.
  3. Endpoint model: distinguish communication methods such as SMS and voice from transports such as QUIC and SIP. Define endpoint ownership/verification and capability reporting.
  4. Freshness: distinguish user-declared availability from observed connectivity, and define expiry, offline and unknown behavior.
  5. Preferences: choose defaults, temporary overrides, optional schedules/time zones, precedence and permitted fallback. A delivery timeout must not silently cause an unwanted second contact.
  6. Access and updates: specify who can discover endpoints and availability, who can update them, and how SDK/API clients receive changes. Detailed personal schedules need not be exposed to senders.

Recommended direction for review: Connect stores identities, endpoints and preferences; rvoip supplies registration/lifecycle primitives; UCTP defines interoperable reachability/presence exchanges. Reuse existing types where their meaning fits, and propose versioned extensions for missing behavior. This recommendation is not yet a settled decision.

What completion would have to prove

Draft acceptance questions to settle with the scope decision.

  • One identity has several authorized communication endpoints and can be contacted through the selected method.
  • The owner changes a preference through a public interface; subsequent routing observes it.
  • A temporary override expires and the previous/default preference resumes.
  • Disconnects and stale observations do not falsely advertise availability or remove a durable SMS/inbox route.
  • Updates, reads and subscriptions enforce current authorization, with restart behavior explicitly tested.
  • A sending agent can understand whether a route was selected, unavailable, prohibited or uncertain without being told unrelated private endpoint details.

B-002 · Conversation memory selection and source precedence

Gate 3 retains original history and supplies a bounded, attributable model view. Live tests exposed omission of older facts and a phonetic telephone rendering of Quartz Harbor as courts harbor. The current qualified test recalls four route-specific decisions plus the original draft facts after restart. An earlier assistant prompt wrongly treated prior history as an exclusive snapshot and rejected newly spoken facts; the shipped prompt now accepts live dialogue and current corrections. Historical failures remain attributed.

Before expanding Gate 4 context tools, decide summary/pinned-fact ownership, authorized retrieval, source precedence and handling of ASR confidence. Derived corrections must retain their originals; quoted provider content must never become elevated instructions.

Read actual observations. This is a future memory-quality decision, not an unrecorded waiver of Gate 3 continuity.
