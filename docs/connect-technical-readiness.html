01

The fastest credible route is composition.

Start with Parley’s conversation model and durable state. Add a native QUIC path on the same command handler. Bring in selected Bridgefu patterns and learn from Thelve without adopting either complete product.

The pieces are substantial. The work is to give them one durable identity, one public contract, and a repeatable installation that developers and agents can actually use.

Reuse the engine.

rvoip already contains QUIC control/media, SIP, WebRTC, and a Vapi audio adapter. Rewriting these would distract from Connect’s product work.

New Connect work

Build the product surface.

Stable app/agent presence, a complete SDK, transport parity, generic connectors, agent installation, and account setup still need a Connect-specific contract and proof.

Native SDK implementation · Connector contribution boundary

Scope stays as agreed: server and SDK first; Vapi and Telnyx; SIP, PSTN, SMS, WebRTC, messages, files, voice, and video; one additional assistant integration. The app journey uses the same foundation. The permission-console proposal is not part of this plan. Retain scoped access, delegated authority, activity records, and revocation without routine approval prompts.

02

What each project should contribute.

Use the current GitHub source as the audit baseline. Preserve local working checkouts; source links below are pinned to the inspected commits.

Primary adaptation candidate

Parley

Contribution: SQLite conversation/session/message state, durable conference journal and deliveries, a browser/Node UCTP client, Vapi chat and voice orchestration, and a persistent external assistant worker.

Boundary: the conversation-control/1 profile is experimental and WebSocket-only. Generalize conference participants, roles, routes, and setup; do not ship lab defaults as Connect onboarding.

Parley state · Conversation profile · JavaScript client · Assistant worker · Provisioning

Direct dependency candidate

rvoip + UCTP

Contribution: shared communication nouns, Orchestrator, QUIC streams/datagram media, SIP/WebRTC adapters, protocol framing and negotiation, and the Vapi audio adapter.

Boundary: native UCTP/QUIC is already integrated with rvoip-core. rvoip-client sends data messages and receives incoming events, while some convenience methods and session actions remain incomplete. Parley’s additional durable application profile still needs QUIC integration.

QUIC datagram implementation · Wire compatibility · WebRTC ↔ QUIC test source · Vapi audio adapter · Native SDK implementation

Selective extraction / adaptation

Bridgefu

Contribution: provider control and normalized events, durable call operations, replay protection, one-use media attachments, SQL repositories, declarative recipes, and a typed browser WebRTC SDK.

Boundary: call-leg and gateway operations need translation into Connect’s conversation model. Avoid importing the split gateway/worker deployment and Redis requirements into the single-process local experience.

Provider control contract · Durable operation repository · Replay and attachment binding · SQLite / Postgres implementations · Recipe manifest · Authenticated UCTP ingress · Browser SDK implementation

Design reference + selected extraction

Thelve

Contribution: authenticated Streamable HTTP MCP, Vapi tool provisioning with durable intent/recovery, carrier bindings, AAuth task authority, and explicit execution evidence.

Boundary: implementations are coupled to workspace roles, business capabilities, Postgres, and product licensing. Select any modules to relicense before copying them into open-source Connect. Use the architecture lessons immediately; keep the operator experience lightweight.

Managed MCP implementation · AAuth contracts · Durable provider provisioning · Carrier bindings · Thelve dependencies / license · Thelve source license

Direct dependency candidate

telnyx-rs

Contribution: typed messaging and SIP configuration APIs, raw-body webhook verification, configurable retry behavior, and provider wire-test fixtures.

Boundary: an API client supplies provider operations, not Connect conversations or delivery guarantees. Submission retries, callback deduplication, and ambiguous outcomes need an explicit host policy.

Messaging API · Webhook verification · SDK retry defaults · SIP provisioning API · Messaging wire tests

New product repository

Connect

Today: the repository has an initial README; the local workspace holds the product contract and experience drafts. No Connect server or SDK implementation was found in this workspace.

04

The gaps that could change the plan.

Resolve these before attaching dates to the roadmap. None is a reason to throw away the existing implementation.

Resolve first

One dependency graph.

Bridgefu pins rvoip 0.3.8; Parley pins 0.3.12 plus a nine-file patch; Thelve carries vendored rvoip overrides. Their Rust types and behavior are not automatically interchangeable.

Action: reproduce Parley’s patched baseline in isolation, decide which patch changes to upstream, and compile any Bridgefu extractions against that exact graph. Preserve the vendored Vapi SDK provenance.

Bridgefu dependencies · Parley dependencies · Conference patch · Vendored Vapi SDK provenance · Thelve dependencies / license

Resolve first

Bring Parley’s application behavior to QUIC.

Base UCTP already has conversation operations wired to rvoip-core over QUIC. Parley adds durable journal, participant-routing and application-command semantics through its WebSocket integration; its profile explicitly says QUIC/WebTransport parity is not implemented or tested. Integrating that additional behavior is the gap.

Action: share one host handler and journal across transports. Prove equivalent authorization, command replay and incoming events, then prove media datagrams independently.

Conversation profile · Conference patch · QUIC datagram implementation · Wire compatibility

Resolve early

Complete the Connect-facing SDK.

Native UCTP/QUIC, its core integration, data-message sending and incoming events already exist. In rvoip-client, send_message() still returns NotImplemented; SessionHandle::accept() does not yet send an acceptance, and reject() is unimplemented. The Parley JavaScript client uses ws/wss; Bridgefu’s SDK is browser WebRTC-specific.

Action: reuse the existing native implementation, complete the client operations Connect needs, and integrate its durable application behavior. A small Rust client tests that composition. TypeScript runtime/binding selection is a separate packaging decision.

Native SDK implementation · JavaScript client · Browser SDK boundaries

Session actions · Message and inbox methods · Existing QUIC-to-core wiring

Fix before live qualification

SMS uncertainty crosses two layers.

Parley’s conference outbox records unknown results, but its send function uses the Telnyx client’s default retry policy. The inspected SDK defaults to two retries and documents that message submission lacks server-side deduplication.

Action: disable automatic submission retries for this operation and reconcile uncertain results. Consolidate the ordinary spawned-send path and the durable conference path before promising restart-safe delivery.

SMS outbox · SMS submission · Telnyx client defaults · Messaging API · SDK retry defaults

Qualify the whole path

The latest demo is partial evidence.

Parley’s committed October 6 rehearsal notes report browser/phone handoff progress but also a phone hangup classified as failure, an unmet duration gate, and real SMS deferred. Private recordings and logs were not inspected here.

Action: preserve the documented failure cases as regression scenarios. Repeat the agreed complete journey on the final Connect dependency graph.

Upstream rehearsal record

Adapt deliberately

Provider setup needs product behavior.

Parley provisioning includes a lab number and can update an existing assistant’s callback. Thelve’s provisioning model offers stronger intent/recovery patterns, but its implementation is coupled to its product.

Action: make resource choice, change preview, readiness, and recovery explicit. Keys start setup; eligible numbers, webhook verification and reachable endpoints complete it.

Provisioning · Durable provider provisioning

Do not infer support from a type name: Bridgefu contains Twilio/Vonage-related code, but its current ProviderRegistry rejects their configuration as deferred. Keep them outside the initial integration promise. Runtime provider restriction

06

First deliverable: a reachable app and agent on native QUIC.

Make the foundation interesting without waiting for carrier approvals. Then add the provider experience on the same conversation contract.

Download one server. Start an agent example and a separate app. Address either one, exchange messages in both directions, restart a client, and continue the same conversation over UCTP/QUIC.

Gate 1 · First usable foundation

Presence you can exercise.

  • One locally persistent server process and explicit local identities.
  • A small native SDK/client with authenticated UCTP/QUIC control.
  • One shared conversation handler; outgoing and incoming app/agent examples.
  • Stable request IDs, durable events, replay checks and cursor recovery.
  • A documented local setup, health output and reproducible demonstration.
Next visible payoff · Gate 2

Bring Vapi and Telnyx.

  • Select an assistant and a messaging-capable number.
  • Use Vapi chat through the same conversation API.
  • Text the assistant from an approved human phone and receive its reply.
  • Let the assistant initiate authorized communication through Connect.
  • Observe delivery state and incoming replies without exposing provider keys to clients.

Do not postpone the differentiator: start the native audio experiment alongside Gate 1. Gate 1’s message exchange proves QUIC control, not datagram media. Gate 3 must demonstrate the latter and the required SIP, PSTN and WebRTC routes.

07

Decisions to carry into the implementation plan.

Recommended defaults are deliberately small. Approve the direction after the experiments provide evidence; avoid defining every future connector now.

  1. Use Parley as a donor, with Connect owning its public contract.

    Extract useful conversation and delivery behavior; remove conference-specific assumptions rather than inheriting the entire demo application.

  2. Choose one rvoip graph and one transport-neutral application handler.

    Prefer a reproducible 0.3.12-based path if E1/E2 pass; document required patches and upstream work. Do not combine mismatched workspace overrides.

  3. Prove the native interface in Rust; validate the first developer SDK choice.

    TypeScript remains the proposed first product SDK. Compare a supported native binding/runtime or another explicit packaging approach before promising QUIC parity. A browser WebRTC path is a separate supported profile.

  4. Start local persistence with SQLite.

    Parley provides a practical starting point. Decide transaction boundaries, event retention and backup/restore before advertising durability; keep external databases optional until evidence warrants them.

  5. Select a Telnyx voice topology.

    Evaluate SIP trunking into rvoip as the initial route, with Bridgefu Call Control as a concrete alternative. Pick the one that meets setup and lifecycle requirements with the least extra machinery.

  6. Use a small connector contract with media-specific extensions.

    Describe configuration, readiness, supported operations, external IDs and event normalization. Reuse rvoip for live media; design asynchronous delivery separately. Avoid forcing SMS into call-leg abstractions.

  7. Retain delegated access without a permission-console project.

    Centralize credential scope, task/conversation binding and revocation in the server. Use Thelve’s lessons without importing its full business registry, approval UI or deployment stack.

  8. Resolve licensing before source extraction and publication.

    Record source provenance and notices. Select any Thelve modules to relicense under the chosen Connect license, or build Connect-specific implementations from the agreed contracts. This audit copies no implementation into Connect.
