# Private SIP context purposes

Private consultation context validation distinguishes media, signal, and
presence. Each purpose validates the original canonical connections, runtime,
generation, credentials, native keys, Endpoint and Device, membership epochs,
current presence, reciprocal private partner bindings, and recipient ceilings.
A physical SIP descriptor remains tied to its original registered call and own
private consent. Metadata validation does not create a reader or grant IO.

Media additionally requires the existing audio, offer and receive subscription
permissions. Signal context does not inherit those requirements. Named
`dtmf.send` and `dtmf.receive` checks still belong to each directional signal
reader. Signal cannot run from preparation: a pending context needs captured
applied audience state and current original execution authority. Once sealed,
the recorded physical lifetime validates its current authorities independently
of the old execution credential. Restored, handed-off, unavailable provider and
foreign-runtime contexts remain closed.

The source-current check for attributed observations uses presence context;
media permission withdrawal alone does not invent a physical departure. Current
source credentials, epochs, private audience and observation permissions still
apply separately.

A public native primary acquires the complete context when it carries a private
SIP floor. Its owned signal reader therefore fences the independent SIP route
owner as well as the native and private principals. A cloned interval remains
owned until its final reader drops. A held public remote keeps its own scopes.
Candidate registration is also checked before a physical content floor exists,
so cancellation cannot expose an unprepared native candidate as an ordinary
observation source.

This increment provides internal context and scope derivation. It does not
install private SIP-candidate signal or packet readers, coordinator selection,
host lifetime handoff, or actual private INFO/RFC4733 and return qualification.
G6-046 and its two remaining DTMF clauses stay open. Existing public commands and
operation recovery remain documented in the [server HTTP reference](canonical-http.md).
