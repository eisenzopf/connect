# Inline EdDSA and ES256 signatures

The canonical verifier implements Ed25519 (`EdDSA`) and P-256/SHA-256 (`ES256`).
`Sig9421Signer::ed25519` and `::es256` load private PKCS#8 keys through `ring`;
the latter validates the named P-256 curve and matching public component.
`algorithm()` reports the actual signer. Diagnostics contain no keys or key IDs.

ES256 uses the JWA fixed-width 64-byte `R || S` signature, base64url without
padding. Public keys are 65-byte uncompressed SEC1 P-256 points. ASN.1 DER
signatures, wrong curves, malformed points, truncated signatures and algorithm
substitution fail. An ES256 signature does not establish a new authentication
method or elevate assurance.

Both algorithms sign the JCS bytes of every original envelope field except
`signature`; signing replaces only that field. Verification covers optional
fields, resource and reply correlation, operation identity and expected revision.
The principal-owned, contextual and held-current-key verifier paths share the
same algorithm implementation, key validity/revocation checks, bounded freshness
and atomic replay store. Signing again or changing algorithms cannot make a
consumed envelope ID reusable. A retry requires a fresh envelope ID/signature
and the same logical operation ID.

The challenge advertises the actual implemented algorithms and the existing
`identified` minimum authentication assurance. Anonymous/pseudonymous assertions
cannot establish a durable Identity or fabricate Conversation membership below
that floor. A failed lower-assurance proof can retry with a fresh envelope and
valid installed credential. Higher per-mutation assurance still requires the
current policy and correlated step-up, not a signature algorithm or rank label.
Only installed credential methods are advertised; the current fixture backend
installs bearer. PS256/RS256 and HTTP-header signature processing are not offered.

`scripts/check-gate6-es256.py` records local source-bound runtime evidence in
`docs/evidence/gate-6/es256.json`. Eight crypto cases include independent `ring`
primitive verification of the JWA bytes, a valid same-key DER signature rejected
by the inline verifier, exact current owner/key/algorithm checks, scope/optional
field tampering, freshness, malformed keys and shared replay across signing
algorithms and verifier paths. Canonical peer cases use P-256 proofs/replies,
refresh and replay, an explicit assurance floor, and actual local pinned TLS.
The actual QUIC/WebTransport/WSS exchange case queues a real grant writer,
rejects a wrong Connection reply without consuming the waiter, then verifies
the valid ES256 reply under the still-held key guard without resolver reentry.

The task-level review is `contracts/gate6-authentication-evidence.json` and
[`authentication-audit.md`](authentication-audit.md). The audit checker binds
all 42 auth clauses and the unchanged G6-026 work/verification text to observed
named cases. The review distinguishes reusable authentication behavior from
Connect service installation, persistent logical recovery and independent
conformance. It does not turn test counts into a protocol-conformance claim.
Task status is recorded in the Gate 6 implementation plan after both checks pass.

Credentials, key revocation and resource policies in these tests are controlled
fixtures. Real Connect policy/dispatch, IdentityProvider/EndpointRuntime,
invitation routing, checked media credential rotation, full media negotiation,
durable reconnect/restart, SDK/browser/remote/provider/quality profiles and Gate 6
acceptance retain their assigned tasks. No publication or live provider operation
is part of this qualification.
