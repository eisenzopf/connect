# Core to SIP INFO routing (G6-024 in progress)

An explicit `DtmfIntent` selects RFC4733 or INFO. INFO uses a separate `DtmfInfoWriteScope` and `DtmfRoutePolicy::acquire_info`; it never fabricates RTP clocks, timestamps, SSRCs or payload types. The scope carries the immutable original digits/duration, digit index, actual serialized INFO request and prepared UDP destination. Core adds its exact current source/recipient bindings and original logical operation. Those facts are metadata, not permission. The host acquires current independent signal permission for each actual write.

The SIP adapter captures one exact admitted route generation. The coordinator delegates to its existing dialog adapter, which retains that session's exact dialog and uses the canonical immutable INFO API. Each write checks current mapping, lifecycle, established session and confirmed dialog, then acquires permission and tries the exact state-machine lane. It never waits for that lane while holding permission. The lane and owned host lease span the actual owned IO, including cancellation. A synchronous SIP lifecycle fence, combined with Core's registry/lifecycle/Session/Conversation fences, protects each bounded transport poll and releases synchronous guards on Pending. No permission reader or state lane spans retry timers, response waits or digit gaps. Temporary unavailability of Core metadata is a passive liveness hint, not retirement and never permission. The original schedule can wait within the existing write deadline, acquiring metadata before host permission; each physical poll still requires all exact guards and performs no IO while they are unavailable. Actual retirement, cancellation and expiry remain final.

The bounded `application/dtmf-relay` profile accepts one ASCII DTMF digit and an explicit 100–5000 ms duration per INFO, with the existing whole-sequence limits (32 digits, 30 seconds including gaps). Validation occurs before any prefix. Each digit uses the existing body helper and sole INFO materializer. The materializer captures the actual dialog Contact as its Request-URI while retaining the distinct remote identity in To and preserving the dialog route set. A real UDP regression first reproduced the incorrect identity-as-target request; the fix reuses the existing enhanced request builder. Retransmissions preserve the exact transaction branch/CSeq/body and reacquire permission. A new digit consumes the next CSeq while retaining the original logical operation. The owned schedule waits for exact final SIP acceptance before progressing and preserves requested quiet time. If an INFO is retransmitted, the next digit waits for the tone duration and gap after the latest possible write; a lost original datagram cannot collapse the spacing when its retry is accepted. This never extends the original absolute deadline. Non-2xx, missing completion, deadline, cancellation or retirement stop the suffix; errors after a submitted prefix preserve uncertainty. No automatic address/authentication retry or raw RFC4733 fallback occurs.

Core retains the existing bounds of 64 active schedules and one per recipient, with one caller-owned cancellation and absolute deadline. Dropping the parent drops the currently owned INFO delivery, aborting pending IO and blocking later transaction retransmissions. Already submitted effects cannot be recalled. A 2xx is SIP acceptance, not evidence of remote tone playback. A 401 remains factual refusal evidence and does not trigger a challenged effect replay.

The installed network profile is UDP. A concrete TCP/TLS/WebSocket route is refused before submission. RFC6086 INFO-package negotiation is a separate profile; this component uses the explicit bounded application/dtmf-relay profile. The raw lower SIP APIs remain trusted standalone primitives, not a fallback route.

`scripts/check-gate6-dtmf-info-route.py` establishes two real local SIP/SDP calls through Core, verifies the exact source/recipient and original operation at every INFO write, compares authorized and received bytes, checks actual Timer E retransmission, withdraws permission during retries and digit gaps, retires only the source while the Session remains active, and tests drop/cancel/deadline, target contention, invalid whole intents, missing routes and a real Digest 401 challenge with configured fixture credentials. A separate actual RTP case holds a Session metadata writer, verifies that no packet is written while it is held, and resumes the same still-authorized schedule after release. It repeats the affected Core, shared DTMF, SIP wire, canonical INFO, transaction and completion checks, then builds the locked Connect server. All fixtures use isolated ephemeral local endpoints.

This does not close G6-024. Sealed [native source](native-dtmf-route.md) and [native recipient](core-native-dtmf.md) composition have separate source-scoped profiles. Richer SIP/WebRTC received-source composition, remaining approved media profiles, downstream production journal/service/HTTP/SDK installation and Gate 6 platform/remote acceptance remain open.
