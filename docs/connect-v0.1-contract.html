Connect v0.1 · For review

The product contract.
The first working conversation.

An open communications server and SDK that make it easy for applications and agents to communicate with people—and with each other.

This draft proposes the first-release promise, the evidence that would prove it, and the decisions needed before scheduling the roadmap. It describes work to build, not capabilities already available.

01

Make communication a capability every builder can use.

Run one Connect server. Give an app or agent an address and permission to communicate. Use the SDK to send, receive, and participate through one shared interface.

Reach out

Connect to people and systems.

Send a message, share a file, or start a voice or video session. Reach participants through native clients, browsers, and configured services.

Be reachable

Expose the same interface.

Let another developer or agent discover supported capabilities and communicate with your application, within the permissions you set.

Proposed release identity: a developer alpha. v0.1 should be useful enough to build with, understandable enough for an agent to use, and explicit about compatibility and operational limits. It should give a new contributor a working foundation to extend.

The immediate audience is app and agent builders. People participate through their existing channels and a small reference client. Service providers can contribute connectors or implement UCTP themselves.

02

One conversation that proves the foundation.

An assistant needs its human’s help choosing between two options. The human can respond, talk it through, and continue afterward.

  1. Start locally and connect two participants.

    A documented command starts the server. The developer connects an agent example and opens the reference client as its human. A companion quickstart installs the MCP tools and Connect skill into a supported agent host. The local example needs no provider account.

  2. Discover how to communicate.

    The agent resolves an address, authenticates, and learns which operations the participant and route support. Permission is checked before communication begins.

  3. Exchange a message and a file.

    The agent sends the two options and an attachment. The human replies. Both clients receive correlated events and can retrieve the conversation’s permitted history.

  4. Talk in the same conversation.

    The agent invites the human into a voice session. The human accepts, communicates, and ends the session. A video variant proves the same invitation and lifecycle model with two video-capable participants.

  5. Reconnect and understand the outcome.

    Disconnect one client, reconnect it, and resume durable events without duplicating a message or call request. A media interruption has an explicit outcome; live media itself is not replayed.

  6. Make an independent application reachable.

    A second, separately written agent or app initiates a permitted conversation with the first. It can use the documented SDK and protocol without private knowledge of the reference client.

Vapi assistants are part of the first release. Configure a Vapi account and assistant on the server. Reach the assistant through the chat API and bidirectional WebSocket audio; prove human voice participation through browser WebRTC and Telnyx PSTN calling. Let the assistant invoke permitted Connect MCP tools during a call or chat. Also demonstrate a SIP endpoint and a two-way Telnyx SMS exchange. Each path must preserve the shared identifiers and report its actual capabilities; SMS is not expected to carry a live media session.

These are repeatable demonstrations with observable results. They do not require a single elaborate call that passes through every provider.

The first agent acceptance test: “Send my human this draft, ask which option they prefer, and continue when they reply.” The agent shares the artifact, receives a correlated reply through the host integration, and continues the original task. This must work through the installed tools, not only through a hand-written SDK demo.

03

Design the quickstart before the internals.

A developer should understand the interface by reading one example. An agent should be able to discover the same operations through structured descriptions.

ContractWhat the caller should be able to rely on
Address & identityResolve a participant or application using a documented address. Keep the actor’s identity separate from the channel used to reach it. Native addressing must not require a global directory.
CapabilitiesDiscover supported media, operations, limits, and permission requirements. Get an explicit unsupported-operation response before starting an impossible interaction.
Conversation & sessionKeep messages, attachments, participants, and live sessions related through stable identifiers. Starting or ending a call does not erase the conversation.
Requests & eventsCorrelate requests with events. Distinguish accepted work from completed work, and provider acceptance from delivery or a human response. State “unknown” where a service cannot confirm an outcome.
Retry & recoveryUse idempotency keys for retryable operations and cursors for durable events. Publish ordering, retention, and redelivery rules. Do not imply end-to-end exactly-once delivery.
Authority & limitsUse scoped application credentials and explicit invitations. Enforce access to conversations and files. Bound outbound calls, messages, concurrency, and usage where operations can spend money.
Illustrative SDK experience

This is proposed pseudocode for discussing the shape of the API. Package names, methods, addresses, and event names are not implemented or fixed.

client = connect(server, credential)

human = client.resolve(human_address)
human.capabilities.require("messages", "files", "voice")

conversation = client.conversations.create([human])
conversation.messages.send("Which option works for you?", request_id)
conversation.files.send(local_file, access = "participants")

invitation = conversation.sessions.invite(human, media = ["audio"])

for event in client.events.resume(cursor):
    handle(event)       // message, invitation, session, or failure
    save(event.cursor)

// The same client can receive an authorized incoming invitation.
client.invitations.on_receive(handle_incoming)
For agents

A communication surface they can pick up.

Ship MCP tools, a Connect skill, and one additional assistant integration selected through research in v0.1, alongside Vapi. Publish structured operations, capabilities, and errors. An agent should be able to install, authenticate, reach its human, and receive a reply without writing integration code.

For developers

Useful defaults, visible boundaries.

Provide a server package, a working SDK, and examples for initiating and receiving communication. Keep provider credentials on the server. Let callers inspect provider-specific details when they actually need them.

Proposed communication tools

Names are illustrative. Keep tool schemas small, return stable identifiers, and distinguish accepted, delivered, replied, failed, and unknown outcomes.

ToolIntent
resolveFind a configured person, app, or agent; discover its permitted channels and capabilities.
send_messageInitiate or continue a conversation with a retry-safe request identifier.
send_fileShare an artifact with the intended participants and explicit access.
read_conversationRetrieve permitted history, replies, and outcomes.
start_sessionInvite participants into voice or video and return a session identifier.
wait_for_eventsWait for a bounded period or resume from a cursor to receive replies, invitations, and session changes.
The Connect skill

Teach the workflow.

The tools expose actions. The skill teaches an agent when and how to combine them: resolve a known contact, use an authorized channel, share an artifact, interpret delivery state, and continue after a reply.

Include short workflows for asking a human, communicating with another agent, and starting a session. Explain retries, missing capabilities, and when to ask the user for clarification. A skill cannot grant permissions or override the host’s rules.

The incoming reply

Return to the right task.

Connect persists and correlates events. A host adapter maps a conversation or request to the originating agent task and delivers the reply or resumes execution when the host supports it.

MCP installation alone does not guarantee background wake-up. Qualify the selected additional assistant integration for v0.1; provide explicit polling or event-wait behavior elsewhere. Receiving a message does not automatically authorize its instructions.

MCP gives agents access to Connect. UCTP connects the participants. Tools establish and control voice/video sessions; the SDK or media adapter carries live media to a capable runtime. Keep media packets out of individual tool calls.

Distribution should bundle the MCP configuration, skill, setup instructions, and a local demonstration. The skill can be outlined alongside the quickstart; its executable examples must follow the actual tool contract. Background delivery and permissions remain host-specific.

Integration references: skills around MCP tools · function calling · Codex MCP support.

The native transport matters. v0.1 should demonstrate UCTP over QUIC with reliable control and live media datagrams. Browser participation can use the supported WebRTC path; WebTransport and fallback profiles should be qualified explicitly. Connectors will still speak the external protocols their providers require.

The standards ambition needs both a useful implementation and a precise contract. Document which media can tolerate loss, how congestion is handled, and how a native peer negotiates a compatible profile.

05

A proposed boundary for v0.1.

Start with an installable developer alpha and a small, tested set of communication paths. These are proposed release commitments for review.

Proposed v0.1 commitment

Ship a foundation people can use.

  • One server process with a documented local setup, persistent state, health checks, and a restart story.
  • A first SDK and examples for both outgoing and incoming communication.
  • Messages, files, voice, and a minimal video conversation on named, tested paths.
  • A native UCTP/QUIC profile plus SIP and browser WebRTC interoperability.
  • Vapi assistants: chat API access, bidirectional WebSocket voice, PSTN participation, and permission to invoke configured Connect MCP tools during calls and chats.
  • Telnyx PSTN calling and two-way SMS, alongside native SIP and browser WebRTC support, available in v0.1.
  • A connector template, capability manifest, and shared test harness.
  • A reference client and machine-readable API materials for agent use.
  • MCP tools, a Connect skill, a thin JSON CLI, and one additional assistant integration selected from the research shortlist that returns replies to the original task.
Outside this initial commitment

Give the first release a finish line.

  • A hosted communications business with billing and service-level guarantees.
  • A finished consumer messenger or contact-center interface.
  • Global identity directories and unrestricted federation between servers.
  • Every provider, SDK language, deployment platform, and media topology.
  • A connector marketplace with automatic installation of third-party code.
  • Automatic parity between SMS, telephone calls, and richer native conversations.

Confirmed initial integrations: Vapi and Telnyx. Both are required for v0.1. We will also research existing assistants and select one additional assistant integration for v0.1. That selection does not replace either Vapi or Telnyx.

Selection gates

Prove the complete loop.

Require a supported way to install communication tools, authenticate to Connect, maintain task correlation, deliver an incoming reply, and continue the correct task. State whether continuation is automatic, explicitly resumed, or based on bounded waiting.

Run the same artifact → question → human reply → task continuation example against each serious candidate. Sending alone does not pass.

Research output

Choose one with evidence.

Record official source links, tested versions, installation steps, extension/licensing constraints, permission behavior, and the outcome of the example. Compare setup effort, reliability, maintenance burden, and usefulness to the intended users.

Recommend one additional assistant for v0.1 and explain the tradeoffs. Record deferred candidates for later releases; do not choose a winner from name recognition alone.

Telnyx API foundation: telnyx-rs. Assistant research must distinguish the model provider, the assistant product, and the host that actually executes tools and resumes work.

Vapi is a participant and a caller of Connect tools.

Connect can reach a Vapi assistant, and that assistant can use Connect to reach other participants. Both directions belong in v0.1.

Example: a person speaks to a Vapi assistant through Connect. The assistant uses a Connect MCP tool to send the agreed summary by SMS through Telnyx, then reports whether the request was accepted. A subsequent delivery event or reply updates the same Connect conversation.

Connect must map call, chat, tool invocation, and conversation identifiers explicitly. Authenticate MCP requests and scope them to the authorized conversation; provider correlation headers are not credentials. Sharing an assistant configuration does not by itself prove that voice and chat share history. Qualify context transfer separately.

Provider documentation: WebSocket audio · chat API · chat context · Telnyx SIP integration · MCP tools inside Vapi assistants.

Video remains part of the product contract. Before setting a date, name the v0.1 topology, codec/profile, and endpoints we will qualify. The same principle applies to voice and every connector.

06

What would make the release real?

Each claim needs a runnable example or a repeatable check. Success includes the failure and recovery behavior.

  • First connection: a new developer follows only the published quickstart and runs the local conversation without provider credentials. Record the time and points of confusion.
  • Incoming communication: a second app can find a documented endpoint, authenticate, and initiate an allowed interaction.
  • Media: message/file exchange, bidirectional audio, and the selected video path complete between distinct clients with documented limits.
  • Native transport: independent client and server processes exchange UCTP control and datagram media over QUIC; traces show the negotiated profile.
  • Vapi voice: a configured assistant exchanges audio over its WebSocket with Connect and completes conversations with a browser participant and a person reached over Telnyx PSTN. Connect reports session lifecycle and provider failures.
  • Vapi chat and tools: complete a multi-turn chat and an authorized Connect MCP action from both a Vapi call and chat. Correlate messages, tool results, and provider IDs with the correct Connect conversation.
  • Telephony and messaging: inbound and outbound Telnyx PSTN calls, SMS sends and replies, SIP endpoint calls, and browser WebRTC participation pass live checks. Delivery and session events are correlated with the originating request.
  • Recovery: client disconnects, server restarts, duplicate requests, and provider timeouts produce documented outcomes without accidental duplicate calls.
  • Permissions: unauthorized reads, file access, invitations, and outbound operations are rejected; credentials and sensitive content stay out of default logs.
  • Extensibility: a contributor implements a small connector from the template without changing the server’s core and passes the shared contract checks.
  • Additional assistant integration: the assistant selected through research uses installed tools and the supported workflow package to send its human an artifact, ask a question, receive the reply, and continue the correct task. Installation follows published steps without user-written integration code.
  • Shared behavior: SDK, MCP, and CLI paths enforce the same permissions and report compatible identifiers, errors, and outcomes. The skill’s examples run against those interfaces.
  • Honest release: installable artifacts, compatible versions, tested paths, operational limits, and working examples agree with one another.

Network-loss tolerance, latency, concurrent sessions, file limits, retention, and restart recovery need measured targets after the first experiments. A release must publish its tested envelope; this brief does not invent performance numbers.

08

The decisions to review first.

These recommendations make the next round of planning concrete. They are choices to discuss, not decisions already made.

A

Who is v0.1 for?

Someone building an application or an agent that needs communication and needs to be reachable.

Recommendation

Lead with the server and SDK. Use the reference client to test the experience and teach integration.

B

Which SDK comes first?

TypeScript supports web applications and the reference client. Python matters for many agent builders.

Recommendation

Define a language-neutral contract, implement TypeScript first, and prove a Python agent can use it. Decide whether v0.1 requires a packaged Python SDK or a documented API example.

C

What does “one process” mean operationally?

The server should combine communications responsibilities without forcing a new user to assemble a service stack.

Recommendation

Aim for a self-contained local mode with persistent data. Choose its storage and the production database options after the reuse audit; make backup and restart behavior explicit.

D

What must the first media release prove?

Messages, files, voice, and video need a specific compatibility matrix, not an unbounded promise across every service.

Recommendation

Start with a minimal two-party media profile, native QUIC evidence, browser participation, and named SIP interoperability checks. Qualify richer mixing and video topologies separately.

E

How open is the extension surface?

Developers need to add connectors. Independent implementations need enough protocol detail to participate.

Recommendation

Design the connector contract alongside Vapi and Telnyx. Publish the supported UCTP profile and conformance examples. Choose the code/specification licences before accepting outside contributions.

F

Which agent host proves the first loop?

A tool call can send a message. The selected host must also support a documented way to deliver the reply to the right task.

Recommendation

Research Meta Muse, Grokbot, OpenClaw, Codex, and other suitable assistants. Verify product identities and extension paths, run the same complete conversation test, and select one additional integration for v0.1. Vapi and Telnyx are already confirmed.

Next artifact after review

The quickstart we want to make true.

Once this contract feels right, write two quickstarts: a developer builds with the SDK, and an agent uses the installed tools and skill. Then audit the existing code and host integration options against both. That evidence will turn the roadmap into a sequence we can build and verify.
