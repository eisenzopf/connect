Connect · Pre-Gate 4 · R08 decision record

Tasks have authority.
Conversations have continuity.

The conversation remains the durable home for context. A task is a separate unit of delegated work, with a server-enforced binding to that conversation.

Decision closure, not a claim that the Gate 4 task runtime or MCP server is implemented. These choices become mandatory implementation and acceptance requirements for Gate 4.

October 12 amendment: decision 010 makes ordinary revocable identity access the default local agent installation. The task/grant decisions below remain the contract for optional scoped delegation and verified provider invocations. Tasks are optional work tracking; normal communication does not require a new grant for each task.

The selected direction

Use explicit task bindings, narrowly scoped invocation grants and durable inbox delivery. Keep the existing SDK/API and UCTP/QUIC foundation. No per-action permission console or automatic conversation splitting.

Vapi is the first provider/tool host. The public SDK worker pattern used by the review-loop example is the reference durable task runner. Gate 4 will attach Vapi tools to that runtime; selection of an additional assistant remains the separately planned G4-A research decision.

What the server must bind

IDDecision
T-01 · Task identityA developer creates a task under a Connect actor and conversation. The server persists task ID, owner, conversation, permitted operations/recipients, lifecycle state, expiry and initiating event. Starting a call creates a session in that conversation; ending a call does not end the task or conversation.
T-02 · Invocation authorityBind the verified provider call/chat, tool invocation and task on the server. Mint a short-lived opaque invocation grant that narrows the current actor credential to this task and conversation. A model-supplied conversation ID or correlation header never selects authority. Check current credential, membership, task state and grant on every operation and replay.
T-03 · Reply routingTwo tasks may share participants and a conversation. Explicit reply-to/event bindings select a task. Phone/SMS sender matching alone cannot select among tasks. Unbound or ambiguous replies remain in conversation history and are surfaced as unassigned; no guessing, cross-task consumption, silent new conversation or automatic fallback channel.
T-04 · Resume semanticsChoose automatic durable resume for the reference runner: commit an inbox event and task transition before acknowledging delivery. Notifications only prompt a journal read. Disconnected runners resume from durable checkpoints. Vapi tool requests wait at most ten seconds; unfinished work returns a task handle/pending outcome. Later delivery uses the task’s authorized route, not an invented continuation of an ended call.
T-05 · One logical effectPersist an effect key derived from task, step and logical mutation before external work. Retries and restarts reuse it. Unknown provider outcomes require reconciliation; they do not authorize a fresh request ID. Duplicate replies cannot advance a task or perform a business effect twice.
T-06 · Bounded recallKeep the initial 32 KiB bounded context projection and explicit omissions. Add task-authorized paged history retrieval within the bound conversation. Return source IDs, timestamps, provenance and continuation. Retained source history is authoritative; provider observations are attributed evidence, not instructions. No automatic summary or pinned-fact memory is promised for Gate 4.
T-07 · Stop and revokeCancellation or revocation invalidates invocation grants and denies replay; retained receipts remain inspectable only with current permission. STOP blocks SMS dispatch without deleting the conversation or automatically cancelling unrelated work. Reviewed SMS task eligibility is checked again at dispatch, even after a host successfully called a tool.

Required Gate 4 acceptance

These are future runtime checks. They are not marked as passing by this decision record.

  1. Run two concurrent tasks with the same participants, including two tasks in one conversation. A grant or reply for one cannot act for the other.
  2. Reject a forged conversation ID, provider correlation header, wrong call/chat binding, expired invocation grant and revoked credential, including replay of previously accepted operations.
  3. Crash between inbox commit, business effect and acknowledgement. Restart resumes the right task and produces one logical effect.
  4. Deliver duplicate, reordered and ambiguous human replies. Preserve history and show unassigned replies without guessing a task.
  5. Place a required fact outside the initial context window. Retrieve its authorized source through the tool without exposing another conversation. Return explicit unavailable/omitted when access or retention prevents retrieval.
  6. End a voice session, restart the server/runner and continue the same task by another approved channel. Prove context and binding, not merely matching IDs.
  7. Apply SMS STOP after a task queued its update. Deny dispatch; START only restores an otherwise valid reviewed grant. Replaying cancelled work must not resend it.
  8. A slow tool returns pending within its bound. A disconnected host can inspect status and resume from the journal without claiming a completed result.

What closes now—and what comes next

R08 closes the design ambiguity before tools are exposed. Existing conversation authorization, stable receipts, journal replay, bounded context and SMS eligibility are reusable primitives. Gate 4 must still implement durable task records, invocation grants, task-aware tools, routing and host resume, then pass T-A1–T-A8. None is inferred from current conversation-level authorization.

The next product and implementation plans must link these stable decision and acceptance IDs. Their first milestone is the task authority model; tool installation comes after it.
