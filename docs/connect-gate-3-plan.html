Connect carries the interaction.

A developer uses the SDK to continue an existing conversation over native QUIC, a SIP phone, a Telnyx telephone route or browser WebRTC. The same conversation retains the messages, shared artifacts, session history and authorized context.

Starting point · Gates 1–2

Durable messages and provider control.

The current server supports identity, scoped credentials, history, recovery, Vapi chat and direct Telnyx/Vapi telephone control. The qualified telephone audio route is handset ↔ Telnyx ↔ Vapi; Connect journals and controls it.

This gate

Media through the local server.

Connect hosts the session and bridges the actual audio. The existing direct route stays separately labeled. Basic file transfer, availability and context continuity make this useful through public SDKs and a small human test client.

This is a bounded two-party implementation of the broader VoIP 3 model. It does not claim multiparty mixing, live human handoff or seamless cross-device transfer.

One conversation, before and after the call.

  1. Start with an existing conversation.

    The developer selects its ID. An app sends a text draft as an authorized artifact and a distinctive fact the assistant will need.

  2. See what is possible now.

    The SDK reports permitted route capabilities and fresh availability. Unknown is different from unavailable; an optional route preference does not trigger automatic fallback contact.

  3. Invite the assistant into voice.

    Create a Session under that conversation. Use native QUIC, an explicitly mapped SIP/PSTN route or browser WebRTC. Configured agents may accept automatically under their existing authority.

  4. Continue with the earlier context.

    Ask about the draft and prior fact. The assistant must demonstrate access to the relevant information, not merely share a conversation ID.

  5. Make a decision and end the call.

    A permitted voice outcome joins the timeline with provenance. Ending the session releases media resources while retaining the conversation.

  6. Restart and follow up in messaging.

    The assistant uses the recorded voice decision. A contrasting second conversation stays isolated. The developer can explicitly start a new conversation whenever that is the intended boundary.

The app journey uses the same foundation: a review app can share its draft, receive an independent invitation and continue after a restart through the public SDK. Automatic external-assistant task resumption and MCP/skill packaging are Gate 4.

The conversation owns the continuity.

Conversation · persistent cid ├─ Messages, artifact references and accumulated context ├─ Session A · bounded sid │ ├─ Human connection · QUIC / SIP / WebRTC │ └─ Assistant connection · Vapi WebSocket └─ Session B · a later engagement, same cid └─ New connections and streams as needed

Lifecycle contract.

Persistent is the Connect default. A new provider call, assistant runtime, connection or session does not create a new conversation. The developer or its explicitly configured application policy owns creation and closure. An ambiguous inbound caller stays unresolved; caller ID alone cannot grant access or select private history.

The UCTP draft allows persistent and ephemeral policies. Gate 3 uses persistent behavior; automatic ephemeral closure is not required here. Closing a conversation and deleting retained data are separate operations.

Context contract.

Retain source history and context according to declared access and retention rules. An assistant receives an authorized, bounded selection with source references and a watermark. Store submission, failure and observed outcome separately. Bounded context does not bound the conversation.

File bytes are not automatically language-model input. The text-draft demonstration supplies authorized text or a supported extraction; unsupported formats remain attachments with explicit limits. Missing voice outcomes must be visible, not invented.

Model references: VoIP 3 overview · six-noun model · UCTP lifecycle §§7.1–7.4. These are design sources; qualification must use the pinned implementation. Recording/vCon capability is assessed in the reuse mapping and is not evidence that every provider automatically supplies a complete transcript.

A gate with a clear finish line.

Required here.

  • Persistent conversation/session/connection semantics and useful bidirectional context continuity.
  • Two-party native QUIC audio to Vapi; SIP endpoint; inbound/outbound Connect-carried Telnyx PSTN; browser WebRTC.
  • Reliable basic files, current access checks, integrity, lifecycle and backup consistency.
  • Basic availability and a small expiring preferred-route override.
  • Public SDK/media bindings, human test client, local installation and recovery qualification.

Preserved for later.

  • Live SMS: resume G2-018/G2-019 after approval; still required for full v0.1.
  • Gate 4: additional assistant research/selection, MCP, skill and automatic task continuation.
  • Gate 5: video implementation, complete contributor kit, independent protocol conformance and full release.
  • Backlog: rich schedules, automatic channel fallback, permission console, full contact registry and multiparty/handoff UX.

The broader model can represent more than Gate 3 qualifies. Basic availability does not close every part of B-001. G3-006 selects a minimal future video profile without advertising video as implemented.

Durable VoIP 3 conversation model

One persistent cid spans messages, bounded sessions and replacement connections. Session end cannot close it. Explicit developer create produces a separate conversation. Upgrade preserves existing history/receipts; all six nouns have one documented owner.
