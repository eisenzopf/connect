Two complete journeys. One foundation.

The finish line is a developer who can install Connect, understand what is supported, and complete either journey through the same identities, conversations, authority and event model.

Journey one · Agent

Give an agent presence.

Reach a configured assistant from an app, a browser or an approved phone route. Let it share a draft, ask a question, receive the answer and continue the right task. Messages, files and live sessions stay related, with explicit context transfer.

Vapi participates through chat and voice and can invoke Connect tools. One additional researched assistant installs those tools and the workflow package without bespoke integration code.

Read the agent experience
Journey two · App

Make an app reachable.

An app can ask its reviewer a question and accept a separately initiated conversation. It shares authorized artifacts, applies its own business permissions, and recovers replies across restarts without repeating a decision.

The native app loop needs no provider account. Configured phone and messaging routes extend the same application logic. A small human reference client demonstrates the public SDK.

Read the app experience

Source commitments: product scope · experience design · readiness and reuse map. Files and video stay in v0.1. A consumer messenger, global directory and connector marketplace are outside this release.

Core tenet · accepted direction

The conversation carries the context.

A person, app or agent can change how they communicate while continuing the same conversation. A voice call is a session within that conversation; ending the call does not end its history or accumulated context.

Six distinct responsibilities.

  • Conversation: durable participants, timeline and accumulated context.
  • Session: a bounded synchronous engagement within it.
  • Message: an asynchronous communication or artifact reference.
  • Participant: who participates, with kind and role.
  • Connection: a participant’s transport binding into a session.
  • Stream: a media flow carried through that connection.

Channel describes how communication happens; it does not create a separate conversation silo. Provider IDs identify bindings, not the conversation itself.

Useful memory across boundaries.

Persist conversation history and context according to declared retention/access policy. Supply authorized bounded projections to assistant runtimes, with source references, version/watermark and delivery outcome. A summary is derived context, not a replacement for retained source history. Context unavailable at a provider boundary must be explicit.

Persistent conversations are the default; only explicit developer/application intent creates a new conversation. New sessions and legs retain the existing conversation. Define ownership, lifecycle and context delivery in G3-A, before media integration. G3-E proves those contracts across the implemented paths. A shared ID alone is not proof that an assistant received or used the context.

Participant identity and authorized conversation membership determine continuity. An ambiguous caller or reply must not be silently attached to someone else’s history.
