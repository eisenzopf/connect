01

A small release with a complete loop.

Gate 1 proves that Connect can give applications and agents a durable communications presence. Vapi and Telnyx then attach to that foundation.

Start Connect. Give an app and an agent identities. Let either one initiate a conversation. Stop and restart a client or the server, then recover the accepted messages without creating duplicate requests.

The demonstration

A review app and its assistant.

The assistant contacts the review app to ask which draft is waiting. The app answers in the same conversation. Later, the app starts a new conversation to ask the assistant to help with another review. The assistant goes offline, reconnects, and receives the waiting request.

The agent example uses a deterministic responder initially, labeled as such. It proves the communications interface; a model is not required to test identity, transport, or recovery.

What ships at this gate

Something a developer can run.

  • A local Connect server and persistent state.
  • A usable Rust SDK for this narrow native path.
  • Separate app and agent example processes using only the public SDK.
  • CLI setup, diagnostics and scoped credential management.
  • A versioned experimental application profile and runnable conformance cases.

Gate 1 is an intermediate delivery, not the full v0.1 release. Vapi, Telnyx, SIP, PSTN, SMS, WebRTC, files, voice, video, MCP, a skill and one additional assistant integration remain in the v0.1 contract. No permission-console product is added.

02

Reuse the stack. Own the application behavior.

Native UCTP/QUIC and its integration with rvoip-core already exist. Connect’s work is the durable product contract, the missing client conveniences, and consistent application handling across transports.

Recorded Gate 1 decision: SQLite owns accepted application state. The application service commits a durable operation before acknowledging it. The frozen wire contract deliberately creates no duplicate rvoip-core conversation projection for messaging. rvoip owns transport runtime; the voice gate will define Orchestrator/session/media ownership and projection recovery where needed. For Connect-owned application commands, exactly one handler executes the mutation; do not let the stock conversation handler and a new handler both execute it.

Reuse baseline and exact boundaries

Start from the readiness-map snapshots, not moving branch tips. First reproduce Parley’s patched rvoip 0.3.12 baseline. Record the minimal changes Connect requires and either upstream them or pin a reproducible patch/fork. Avoid arbitrary sibling path dependencies in the deliverable.

Existing QUIC → core dispatch · Existing conversation operations · Parley application patch · Parley durable store

Bridgefu’s 0.3.8 graph and Thelve’s vendored overrides are references, not dependencies to merge wholesale. Gate 1 need not import either product. Preserve source notices; select any Thelve code for relicensing before extracting it into Connect.

03

A precise first public contract.

These are proposed application operations. Milestone M0 maps them to existing UCTP messages and names any necessary extensions. Reuse current wire meanings; do not redefine an existing operation under the same version.

OperationInput / resultRequired behavior
Resolve identityAddress → stable identity ID and permitted declared capabilities. Runtime availability remains an open v0.1 requirement.A local alias resolves only at an explicitly configured server. Visibility is permissioned; availability does not determine whether a durable inbox exists.
Create conversationParticipant IDs + request ID → conversation ID.Caller must be permitted to initiate with those recipients. Gate 1 freezes the participant set after creation; later membership changes require a separate contract.
Send messageConversation ID + body + request ID → message ID and accepted receipt.Sender comes from authenticated context. Persist the message and recipient-visible events atomically before acknowledging acceptance.
Read conversationConversation ID + page cursor → authorized messages and outcomes.Enforce membership on every request, including reads of previously cached results.
Resume inbox eventsOpaque cursor + bounded page/wait → events and next cursor.Receive both replies and independently initiated conversations. Persistent cursor recovery is authoritative; a live notification is a wake-up hint.
Read operationRequest ID → accepted, rejected, or not found.A connection timeout is unknown to the client, not proof of rejection. Query or retry the identical request to recover its receipt.
Close conversationConversation ID + request ID → terminal conversation state.Reject new sends after closure. Retain authorized history according to retention policy.
Local administrationCreate identity, issue/revoke credential, health and state diagnostics.Separate administration from app credentials. No agent can grant itself scope or impersonate another identity.
Identity and address

Stable across connections.

Use an immutable identity ID plus a server-local alias such as connect:reviews@local. The endpoint and pinned server identity come from client configuration. A conversation participant references this identity; it is not recreated on each socket connection.

Scope credentials to one identity and allowed operations/recipients. Enrollment happens during explicit setup. Ordinary work within that scope proceeds without repeated approval prompts.

Durable result

Accepted is a specific promise.

An accepted message is durably stored with an event available to the intended recipient. It does not mean the recipient’s app has processed it, a human read it, or a provider delivered it.

Gate 1 retains messages, receipts and events without automatic expiry. Publish storage limits and fail explicitly before accepting writes that cannot be retained. Later retention changes must preserve the retry contract.

Request IDs, cursors, storage and authority
  • Logical operation ID: persist before sending; uniqueness is scoped to the authenticated identity. Store a canonical input digest and result. Identical retries return that result; changed input returns a conflict. Recheck current authority before disclosing a saved result.
  • Wire correlation: record the mapping between a UCTP envelope ID and the logical operation. Transport retries must not silently generate a new logical request. Fresh reads use fresh envelope IDs.
  • Event cursor: opaque and scoped to the authenticated inbox. Delivery is at least once, ordered by the server journal for that inbox. Clients must deduplicate event IDs and save their cursor after durably handling or enqueueing the event.
  • Subscription behavior: reconnect and drain pages from the durable cursor. A disconnect between catch-up and waiting must not lose events. Multiple consumers can observe the same inbox; Gate 1 promises no automatic work partitioning.
  • Database tables: identities, credentials, conversations, participants, requests, messages, and journal events. Commit related application changes in one transaction. Persist credentials as verifiable hashes where appropriate; keep signing material and private keys protected separately.
  • Membership and scope: both must permit the operation. A packet’s claimed sender, task ID, or recipient label does not confer authority. Revocation stops future operations and subsequent event batches on an existing connection.
  • Crash recovery: committed messages survive; in-memory notifications may be lost and are regenerated from the journal. The external app is responsible for deduplicating its own business effects. No end-to-end exactly-once claim.

M0 must choose and document message-size, page-size, queue, request-timeout and idle-connection limits, plus stable error codes such as unauthorized, forbidden, conflict, unsupported-profile, not-found and capacity-exceeded. Limits are configurable implementation choices, not unmeasured performance claims.

04

A native SDK people can build with.

Proposed Gate 1 choice: ship the narrow Rust development SDK first to exercise the existing native stack directly. Keep TypeScript as the intended first broad developer SDK for v0.1, with its transport and packaging decision recorded during this gate.

Reuse

The client already does useful work.

rvoip-client already connects over QUIC, sends data messages and receives incoming events. The lower-level UctpQuicClient also gives direct envelope access. Build the Connect facade on the smallest suitable existing surface.

Complete what the journey needs

Messaging, inbox and recovery.

Implement the missing convenience operations and durable application profile. Incoming session acceptance/rejection is a later voice requirement; it does not need to delay the messaging gate.

Native client methods · Incoming event pump · Lower-level QUIC client

Rust-shaped SDK sketchConceptual design sketch · actual API in docs/SDK.md
let client = ConnectClient::open(config).await?;
let reviews = client.resolve("connect:reviews@local").await?;

let conversation = client.conversations().create(
    vec![reviews.id], saved.create_request_id
).await?;

let receipt = conversation.send_message(
    "Which draft is waiting?", saved.message_request_id
).await?;
// receipt means persisted by Connect, not processed by the other app.

let mut inbox = client.events().resume(saved.cursor).await?;
while let Some(event) = inbox.next().await {
    let event = event?;
    app.enqueue_once(event.id, &event).await?;
    checkpoints.save(event.cursor).await?;
}
// The inbox also receives NEW conversations started by other identities.

The example is illustrative, not compilable API documentation. The implementation milestone replaces it with a built, tested example. Credentials and TLS trust live in client configuration; they are not embedded in source.

Proposed terminal walkthroughConceptual design sketch · actual API in docs/SDK.md
# Terminal 1: create local state and demo identities, then run the server.
connect init --directory ./demo --example review-loop
connect serve --config ./demo/server.toml

# Terminal 2: an independently running application.
connect-example reviews --config ./demo/reviews.toml

# Terminal 3: a deterministic agent communications example.
connect-example agent --config ./demo/agent.toml

# Repeat the demo after stopping/restarting a client and then the server.
connect demo verify --config ./demo/operator.toml

Local initialization writes scoped credentials and trust configuration to protected files; normal output omits secrets. Bind listeners to loopback by default. Trust a locally generated development certificate explicitly rather than disabling TLS verification. Remote exposure and provider callback setup belong to subsequent deployment work.

TypeScript decision at M1: compare an in-process native binding with a separately named local transport helper. Demonstrate packaging, bidirectional events, shutdown and credential handling on the proposed supported platforms. A helper adds a client-side process and must be explicit. A WS-only client may remain a compatibility surface; it does not satisfy a native-QUIC SDK claim. If neither option is credible, record the blocker and revise the TypeScript delivery plan before promising availability.

05

Build in reviewable increments.

Every milestone ends with an executable demonstration and saved evidence. No milestone below is complete yet. Experiments are the first implementation tasks rather than a separate open-ended research phase.

M0 · Reproduce & map → M1 · Start & identify → M2 · Persist & recover → M3 · Native conversation → M4 · SDK & two-way examples → M5 · Release Gate 1

M0 · Locally verified

Baseline and dispatch experiment

Depends on: None

  • Create an isolated build from the recorded rvoip / Parley sources; verify patch and vendored dependency provenance. Run the relevant existing native, conversation, SIP and WebRTC regression checks.
  • Trace stock conversation dispatch and Parley application handling. Choose the minimal extension hook for Connect; map each proposed operation to an existing message or explicitly versioned extension.
  • Write short decisions for dependency pinning, handler ownership, error/limit defaults and the first supported platform. Record any extraction licensing choices.

Exit demonstration: A clean checkout builds the chosen graph. A tiny authenticated QUIC probe reaches the chosen application handler and returns a correlated response. Stock handling remains covered by regression tests.

Deliverables: Dependency lock, wire mapping, upstream patch list and test log. If the hook fails, resolve it here before building the public SDK.

M1 · Locally verified

Server shell and durable identities

Depends on: M0

  • Create init/serve/health/diagnostics commands; configure protected local state, TLS trust and loopback listener lifecycle.
  • Persist identity IDs, aliases and credential scope. Resolve an identity from a separate authenticated client; prove unauthorized discovery fails.
  • Run the TypeScript runtime/packaging comparison. Begin a small fixture QUIC datagram-audio probe using the existing media stack.

Exit demonstration: Restarting the server retains identities. A revoked credential fails on a fresh and an existing connection. Setup requires no external account.

Deliverables: Runnable server, local config fixtures, identity tests, TypeScript decision and initial media-probe result.

M2 · Locally verified

Transactional conversation and inbox

Depends on: M1

  • Implement conversation creation, immutable Gate 1 membership, message send, request receipts and durable journal pages through one service layer.
  • Commit mutations, deduplication records and recipient events atomically. Define close/history behavior and cursor bounds.
  • Add failure injection around commit/acknowledgment and implement snapshot/backup-and-restore verification for local state.

Exit demonstration: Crash after commit but before response; reconnect and retry the same request. Exactly one stored message exists and the original receipt is recovered. A changed request body conflicts.

Deliverables: Storage migrations, application-level tests and saved crash/replay traces. This is not yet the wire acceptance gate.

M3 · Locally verified

Native application path and transport parity

Depends on: M2

  • Connect native UCTP envelopes to the shared service with retained authenticated identity. Make handler selection explicit so each operation executes once.
  • Implement create/send/read/close/inbox resume over QUIC. Preserve the WS profile or add a minimal fixture WS entry point through the same handler for comparison.
  • Exercise disconnects, pagination, late notifications, slow consumers and authorization after reconnect. Publish the experimental profile with its supported wire facts.

Exit demonstration: Two independent native clients exchange messages. A permitted WS observer sees the same durable facts. Replaying a request across transports returns the same result; unauthorized paths produce equivalent denials.

Deliverables: Conformance fixtures, native and WS traces, recovery checks and explicit unsupported-profile behavior.

M4 · Locally verified

SDK and independent app / agent examples

Depends on: M3

  • Finish the Rust SDK facade, typed outcomes, event cursor handling and request-status recovery. Demonstrate explicit cancellation and shutdown.
  • Build the review app and deterministic agent as separate processes using only public interfaces. Each must initiate a new conversation as well as reply.
  • Persist client-side request IDs and work checkpoints. Document at-least-once handling and a deduplicated app job example.

Exit demonstration: An offline identity receives a pending request after reconnect. The sample app resumes its own work without applying the same review action twice. Neither example reads the server database or requires provider credentials.

Deliverables: Compiling examples, SDK documentation, process-level acceptance tests and the recorded two-way walkthrough.

M5 · Locally verified

Package and verify Gate 1

Depends on: M4

  • Produce an installable development artifact for the M0-selected platform, with lockfile, license notices, checksums and a supported-environment statement.
  • Run the full Gate 1 acceptance matrix on a fresh state directory and after upgrade from the previous milestone schema. Confirm logging does not expose secrets.
  • Record the datagram-audio probe outcome and unresolved limitations. Update examples to actual commands and capture the developer walkthrough.

Exit demonstration: A reviewer can install and complete the documented journey without private setup knowledge. All mandatory acceptance checks pass; a package and evidence report identify the exact source revision.

Deliverables: Gate 1 candidate artifact and review evidence. Publishing/distribution is a separate release action; this planning document performs neither.

Keep the native media experiment early: use rvoip’s existing datagram implementation and synthetic audio. Gate 1’s release promise is reliable application messaging; it does not claim voice readiness. Record media findings by M5 and treat an architectural blocker as a prerequisite to committing the voice-gate schedule.

07

Proposed decisions to review.

These choices make the first build concrete. M0/M1 validate them; changing one requires updating the dependent milestones, not quietly changing the release promise.

Recommendation

Rust for the first native development SDK.

This is an explicit intermediate choice. It reuses existing QUIC APIs and avoids making the TypeScript runtime decision the first server blocker. Keep TypeScript in the v0.1 plan; decide its native transport packaging in M1.

Recommendation

SQLite owns application durability.

Use a single local installation boundary initially. Preserve identity and conversation IDs across restart. Keep migrations, backup and capacity behavior part of the release rather than importing Thelve’s Postgres deployment.

Recommendation

Extend UCTP only where needed.

Preserve existing envelopes, negotiation and core integration. Version the Connect application profile and publish conformance examples. Keep rvoip’s package release, envelope version, datagram version and application profile separate.

Recommendation

Basic delegation without a new control product.

Setup establishes scoped credentials and permitted recipients. Record actions and support revocation; do not add a ZoneAlarm-style permission console or per-message approval flow.

Recommendation

Keep provider code behind boundaries from the start.

Leave small interfaces for route capabilities, submission outcomes and incoming events. Gate 1 exercises native peers; Vapi and Telnyx supply the first real external implementations in subsequent gates.

Recommendation

Estimate after the first integration evidence.

M0 gives a reproducible baseline; M1 settles runtime packaging. Use those results to estimate the remaining work. No dates or staffing assumptions are invented here.
