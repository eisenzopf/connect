Preserve these decisions.

  • One durable application authority and atomic effect/receipt/journal transactions.
  • Native Rust SDK plus explicit persistent helper for Python/Node; HTTP and browser WebRTC are named separately.
  • rvoip owns protocol/media runtime. Seven recorded patches and source-lock digests make accepted local adaptations reproducible.
  • Provider adapters avoid storage imports; unknown effects are not blindly repeated.
  • Public-client examples, private ignored state, bounded local checks and preserved historical evidence.

Tighten where it helps contributors.

  • Separate provider-specific validation/context behavior from durable core rules before multiplying integrations (R07).
  • Protocol types and dispatch are centralized: 671-line protocol lib, 733-line store dispatcher, 573-line SDK facade. Split by domain while retaining the one transaction boundary; line count alone is not a defect.
  • Many Python operations return validated dictionaries without type annotations. Add named typing and examples as the SDK stabilizes; do not call runtime validation a typed Python API.
  • Passing Rustdoc with warnings denied is useful but does not require all public items to be documented. Add focused module/public contract docs; avoid a cosmetic repository-wide refactor.

Bridgefu and Thelve remain design references rather than whole-product dependencies. That is consistent with the reuse map: importing their deployment stacks would not improve this single-process product. Independent UCTP conformance remains a Gate 5 proof; use of the same Rust helper in multiple languages does not substitute for it.

R01 · High · Existing gap

Discovery does not describe the capabilities we now deliver.

Product brief: discover supported media, operations, limits and permissions. Roadmap F-16 / G3-A; Gate 3 journey: inspect permitted routes before inviting.

Evidence
Identity creation stores only ["messaging"]. Resolve returns that stored value; no public operation returns a route-aware capability/limit catalog. An isolated test accepted an audio session and still resolved its participant as messaging-only. Media negotiation and rejection exist, but are not a discoverable product interface.
Why it matters
An agent cannot reliably choose files, voice or a permitted route without documentation and installation-specific knowledge. This is a partial Gate 3/product commitment, not a missing QUIC implementation.
Proposed action
Add an authenticated capability query or additive resolve result covering configured route, supported operations/media, limits and caller permissions. Keep declared capability, configured readiness and expiring availability separate. Do not advertise video yet or infer provider readiness from a key.
Exit check
Compare messaging-only and media-enabled installations; different scopes see only permitted capabilities. Unconfigured, unsupported and stale states are explicit. Run the same query through native, HTTP and language clients.
When
Close before Gate 4 tool schemas are frozen.

R02 · Medium · Existing gap

Context-delivery visibility stops at the oldest 100 records.

G3-012 / A3-10: expose bounded context, provenance and submission/outcome separately. Persistent conversations must remain inspectable over time.

Evidence
The query orders context_deliveries ascending and takes 100 with no continuation. The isolated 101-delivery fixture confirms that the newest delivery disappears from context_view; omitted remains zero because that field counts source items, not delivery records.
Why it matters
The history is retained, but a developer or agent cannot use this API to inspect the latest delivery failure in a long-running conversation. This is an observability defect, not evidence that stored context was lost.
Proposed action
Return recent deliveries with an explicit continuation, or provide an authorized lookup/page API by session or delivery ID. Report delivery truncation separately from source omission. Avoid mixing growing diagnostic receipts into model input unnecessarily.
Exit check
Create more than 100 deliveries with distinct timestamps, including recent pending/failed outcomes. Verify newest visibility, stable pagination, authorization and restart through SDK/HTTP.
When
Repair before Gate 4 relies on context receipts.

R03 · High · Existing gap

The reference client can show one conversation while joining voice in another.

G3-026: same-conversation messaging/files/voice, visible context delivery/failure. The example should teach public SDK use and recovery.

Evidence
The page lets the user select or create a conversation, but Join voice supplies only URL and credential. Server WebRTC admission uses its fixed configured conversation; the UI neither checks nor displays that binding. Separately, refresh fetches only the first 100 history messages, ignores the next cursor and filters newer ordinary messages out of context. It never renders context.deliveries or omitted. A Node fixture reproduces the hidden-new-message and hidden-failure behavior.
Why it matters
The recorded correctly configured voice demo remains valid. Changing the displayed conversation can mislead a user about which history the assistant receives. Longer conversations also appear to stop updating. This is a reference-experience gap, not a bypass of server authorization.
Proposed action
Expose the authoritative browser binding and prevent a displayed-conversation mismatch before capture/join; an explicitly locked route is sufficient for this local gate. Add paginated timeline handling, context outcome/omission display, and retained mutation intent for uncertain sends/uploads. Repeated button presses currently generate new request IDs.
Exit check
Configure voice for A, display B and require a clear rejection or explicit switch to A. Show message 101 and recent context failures. Lose a response, refresh/retry with the saved ID and prove one accepted effect.
When
Repair before using this client as the Gate 4 human-reply reference.

R05 · Medium · Qualification / operations

Reachability needs an operational readiness signal, not only process health.

Give an agent presence; F-18/F-19 readiness and failure visibility. G3-011 requires worker failures to reach supervision/shutdown.

Evidence
Provider workers can exit on storage/commit errors. The runtime retains their join handles until shutdown; main waits for an OS signal. Health reports installation ID, schema and profile, not worker/route readiness. Existing Gate 3 evidence also retains an unexplained long-idle inbound telephone reachability failure. Fresh registration passed; that does not settle sustained reachability.
Why it matters
A running server may accept local work while an integration no longer progresses. The qualified short-route proofs are real, but do not justify an always-reachable assistant claim. This was source/evidence review, not a newly injected runtime failure.
Proposed action
Expose per-worker/per-route ready, degraded, unavailable and uncertain status. Observe worker exits promptly; do not automatically retry uncertain provider mutations. Qualify registration refresh and idle recovery locally with a fake registrar; keep any later live soak separately authorized and bounded.
Exit check
Inject a worker failure and prove health/readiness changes promptly while queued intent remains recoverable. Drop/reject registration refresh and demonstrate truthful readiness and bounded recovery. Record the disposition of the prior idle failure.

Include in Gate 4 entry work for dependable task continuation; settle telephone readiness before advertising persistent reachability.

R07 · Medium · Design before expansion

The connector seam is useful, but the core still knows Vapi-specific behavior.

F-13 / G5-B: a contributor adds a connector without changing core conversation/routing logic. Server and SDK remain one coherent product.

Evidence
The connector crate correctly excludes SQLite. However, store route validation special-cases Telnyx/Vapi, session resolution queries Vapi directly, and chat context dispatch is conditional on the literal vapi connector. VoiceConnector request types assume assistant and phone-number IDs. These are practical first-provider choices, not yet the general extension contract.
Why it matters
A second provider with Vapi-like context or voice requirements would need more than composition registration. Adding a Gate 4 host directly into these branches would deepen the coupling the product eventually promises to remove.
Proposed action
Before the next integration, define normalized capability/context/lifecycle contracts and keep provider validation in adapters or registration descriptors. Keep conversation authority, receipts and uncertain-effect decisions in Connect. Use one independent fake connector to prove the seam. Full manifests/templates/conformance can remain Gate 5.
Exit check
Add the fixture through the connector API and composition only, including a context-bearing reply or normalized voice outcome. No edits to core conversation authorization or provider-name switches for that fixture.

R08 · Decision · Design before expansion

Freeze task binding and bounded-memory behavior before exposing agent tools.

G4-B/G4-C and F-15/F-20: Vapi tool calls and human replies resume the right authorized task. VoIP 3 conversation persists beyond any one call or model context window.

Evidence
Current credential Scope contains operations and recipients; conversation membership adds another check. It does not express an originating task/call or a per-invocation conversation allowlist. Context selects recent source items within 32 KiB; original history remains, with omissions reported. There is no automatic summary, pinned-fact retrieval or host wake/resume integration. These are limits/design inputs, not a newly discovered authority bypass or a claim that the recorded continuity proof failed.
Why it matters
Two tasks with the same participants need an explicit binding rule; a model-supplied conversation ID or provider correlation header is not sufficient authority. A long-lived conversation can retain an important fact that is no longer in the initial model snapshot.
Proposed action
Decide the server-enforced mapping among Connect actor, task, conversation, call/chat and tool invocation. Reuse current revocation and durable mutation semantics; no per-action approval console. Select one host and declare automatic, bounded-wait or explicit-resume behavior. Define authorized history retrieval and source precedence before promising long-term assistant recall; richer summarization can remain a separate decision.
Exit check
Two concurrent tasks with the same people cannot consume each other’s replies or exercise unintended authority. Duplicate replies apply one business effect, restart resumes the correct task, revocation still denies replay, and an omitted older fact can be retrieved without leaking another conversation.
When
Required decisions in the Gate 4 product plan, followed by numbered implementation and acceptance criteria.
