Communication that moves the work forward.

Give an assistant a reachable identity and the ability to finish an exchange: share the draft, ask the person, wait for the answer, and continue the original task. Give an app the same ability to initiate and receive work through Connect.

Starting point

The channels already work.

Gates 1–3 and the entry repairs qualify durable conversations, messages, files, native QUIC voice, SIP/PSTN, browser WebRTC, context and the reviewed SMS path within their recorded limits.

This gate

The right task resumes.

Add durable task bindings, narrowly scoped invocation grants, MCP tools, a useful skill and one additional assistant host. Vapi and the public-SDK reference runner remain required.

For the developer

Install, bind, communicate.

Supply a task-scoped credential and install assets. Use the SDK directly, expose tools to an assistant or use the JSON CLI. The developer chooses the task and conversation boundary.

For the person

An answer reaches the work.

Respond through the explicitly selected channel. The assistant keeps the conversation context, identifies the right request and reports a real result, a pending task or a clear failure.

Review boundary: the T-01–T-07 decisions are fixed inputs. This document defines the Gate 4 delivery contract. The task contracts and resource limits are recorded in decision 009; Codex CLI is selected as the additional host. Component progress does not establish the end-to-end acceptance below.

Two journeys. One communication foundation.

Journey A · Agent presence

“Review this draft and let me know.”

An installed assistant sends a draft to its human. Connect preserves the task, conversation and reply binding. After a restart, the answer returns to the original work and produces one visible follow-up.

Journey B · A connected app

“You can reach my application, too.”

A review app asks an independent participant for input. Another person, agent or app can also initiate a request to it. Both directions use public clients, explicit authority and the same durable conversation model.

  1. 01

    Install the tools and skill.

    Use Vapi plus the one selected assistant host. The packaged reference runner resumes automatically; the selected host’s actual continuation mode is disclosed and tested.

  2. 02

    Create the task in an existing conversation.

    A developer binds owner, recipients, allowed operations, expiry and initiating event. One conversation can hold multiple tasks; a voice leg is a Session within it.

  3. 03

    Share an artifact and ask a specific question.

    Preserve one logical mutation ID and a reply-to/event binding. The recipient retrieves authorized bytes; the request and source references join the conversation timeline.

  4. 04

    Wait without losing the work.

    A bounded tool call returns completed or pending. The durable worker catches up from its journal cursor after disconnect/restart. Unassigned replies are visible rather than guessed into a task.

  5. 05

    Act on the reply once.

    Use current authority, the task’s effect ledger and the application’s durable business-effect boundary. Unknown external outcomes require reconciliation; an accepted send is not a completed task.

  6. 06

    Continue across an approved channel.

    End voice, restart and continue through messaging or reviewed SMS with the actual decision in context. Cancellation, revocation and STOP are rechecked before any later effect.

The conversation keeps context. The task keeps purpose.

Application model · UCTP/rvoip remain the communication foundation
Conversation · existing durable cid
├─ History, artifacts, context sources and session outcomes
├─ Task A · owner + scope + expiry + initiating event
│  ├─ Step / logical mutation → one effect record
│  ├─ Reply binding → durable inbox → checkpoint → continuation
│  └─ Verified invocation → short-lived narrow grant
├─ Task B · separate authority and reply bindings, same cid
└─ Voice Session · bounded media; ending it preserves tasks and history

Task state belongs to Connect’s application layer. Reuse the existing conversation, journal, receipts, context, artifacts and session APIs. Do not invent a second conversation store or call a new application task field an upstream UCTP standard.

Task lifecycleMeaning
ready → running → waiting → readyA durable task exists, a runner claims a bounded step, and it may wait for a reply or outcome. A pending tool response describes this state; it does not imply success.
completed / cancelled / failed / expiredTerminal task states with an attributed reason. Cancellation and expiry deny further effects and invalidate invocation grants. Retained history follows existing access and retention rules.
Effect: prepared / dispatched / succeeded / failed / uncertain / cancelledAn effect’s status is distinct from task status. A remote outcome that cannot be determined remains uncertain; recovery does not create a fresh mutation identity.
Unassigned replyA conversation event with no safe task binding. An authorized explicit assignment is journaled. Phone number, sender name or a model-supplied task ID cannot silently choose a task.

G4-002/G4-004 record the typed contracts and resource limits in connect-task/1 and decision 009. Contract changes must update their fixtures and evidence. Concurrent transitions require transaction-level tests. Task terminal states do not close the conversation.

Useful autonomy within explicit authority.

DecisionGate 4 behavior
T-01 · IdentityPersist the task’s owner, conversation, scope, expiry and origin. Task creation is a developer/authorized application operation.
T-02 · InvocationBind provider call/chat and tool invocation on the server; issue an opaque, short-lived grant narrower than the actor credential. Every execution and replay checks current authority.
T-03 · RepliesUse explicit reply-to/event binding. Same participants or channel never imply same task. Keep ambiguous replies unassigned and inspectable.
T-04 · ResumeReference runner resumes automatically from durable state. Vapi waits at most ten seconds, then returns pending. Selected host may use evidenced automatic, bounded-wait or explicit-resume behavior.
T-05 · EffectsRecord task + step + logical mutation before dispatch. Deduplicate known effects and reconcile uncertainty. Arbitrary external systems cannot be promised exactly-once delivery.
T-06 · RecallKeep initial context bounded to 32 KiB with omissions; page authorized older sources with provenance and continuation. No automatic summaries or pinned-fact memory are promised.
T-07 · Stop/revokeInvalidate grants and deny cancelled/revoked replay. Recheck SMS reviewed eligibility at dispatch. STOP does not erase history or cancel unrelated tasks; START cannot revive cancelled work.

This is server-enforced delegation with observable task state. It does not add per-action permission prompts or a permission-management console. The skill explains the workflow; it cannot grant authority.
