How developers update this plan.

Status rules

Keep evidence with progress.

  • Not started: no implementation claim.
  • In progress: name an owner and next action.
  • Blocked: record the blocking condition and the dependency or decision needed.
  • Done: implementation and verification complete, with evidence and completed dependencies.
  • Deferred: record an explicit scope decision. It does not count as done.
Stable identifiers

Update rather than renumber.

Preserve G1-001 through G1-053. Append new IDs for discovered work, or add an explicitly named child such as G1-030a. Update dependencies and acceptance mappings. If completed work is invalidated, reopen it and any affected dependent items.

Files and commands name the verified implementation. Update them when the code or operator sequence changes. Record interface changes in the decision notes and corresponding design documents.

  1. Implement and verify an item.

    Record source commit/revision, exact verification command, outcome and a redacted evidence path. A filename without a result is not sufficient evidence.

  2. Update the source of truth.

    Use this page’s fields and “Save updated HTML,” then replace the repository copy with the downloaded document. Browser changes are not automatically written to disk. Confirm the download completes before closing the tab; if the embedded browser does not support downloads, use a regular browser or edit the source directly. Alternatively, use scripts/update-plan.py to update an existing item and its static card together, or edit the plan-data JSON block and the relevant prose in the source file. The task cards are refreshed from that embedded data when JavaScript runs.

  3. Commit the update with the work.

    Review the document diff, source changes and evidence together. Keep raw logs and credentials in ignored local directories; commit concise redacted summaries under docs/evidence/gate-1/. Git history is the audit history.

  4. Close the milestone explicitly.

    Complete its result item, list any remaining limitations and update the delivery plan’s status. Defer or amend scope transparently; do not turn an unrun test into a pass.
