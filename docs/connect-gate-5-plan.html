A new developer should be able to download Connect, understand its supported paths, complete a real two-way interaction, and build their own integration without private knowledge of our setup.

Agent builders

Connect once. Get work done.

One revocable communication identity, discoverable tools, useful context and an honest account of how replies resume work. Optional tasks add tracking; they are not a permission ceremony.

App developers

Reach out. Be reachable.

Three ways to prove the product.

Journey 1 · Give your agent presence

Ask. Receive. Continue.

  1. Install the local server and the supported host’s MCP/skill configuration.
  2. Give the assistant one communication identity and connect its human through the reference client.
  3. Share a draft, ask a question and receive a correlated answer.
  4. Open a supported voice session; carry its recorded decision into the same conversation.
  5. Restart and explicitly resume the selected host’s exact session; continue from the reply and source context.
  6. Let the human or a separate agent contact it first. Inspect activity or revoke the key without deleting history.

Codex remains the additional supported host. Vapi remains required. Automatic background model wake and support for every assistant are not implied.

Journey 2 · Make your app reachable

One SDK in both directions.

  1. Install the review app example with its own identity and public SDK.
  2. Ask its human to review a draft; map the response to an application record.
  3. A separate authorized client contacts the app first and receives a useful answer.
  4. Add a configured channel without rewriting application conversation logic.
  5. Restart the worker and server; resume the inbox without applying a decision twice.

The local journey needs no Vapi or Telnyx account. App authorization remains application-owned; a received message is not permission to execute arbitrary instructions.

Journey 3 · Contribute an integration

Start with the guide, not the source internals.

A contributor creates a messaging/context adapter and a minimal voice fixture from the kit, declares capabilities and passes contract checks. A separate implementer uses the published protocol to connect a client without the Connect helper. Both exercises reveal gaps in the documentation and extension boundary before release.

Video is part of v0.1. Name the paths.

Proposed starting profile: two participants, one camera stream each, VP8 video with negotiated audio. The reference client supplies a human experience; a native media example proves that video also travels over UCTP/QUIC.

Proposed operating target · D5-01

Start small and measurable.

One two-party session at 640×360, up to 30 frames/second, on the named local topology. Demonstrate at least 24 decoded frames/second in the clean profile for 60 seconds, and bounded recovery under the existing 3% loss / 100 ms delay-variation rehearsal. Session teardown stays within five seconds.

Freeze bitrate, packet-size/fragmentation, keyframe, queue and A/V synchronization limits in the implementation profile before coding. Measure resource use and additional concurrent sessions; do not turn targets into advertised capacity without results.

Continuity and capability

Extend the existing session model.

Keep invite/accept/reject/end, participants, connection bindings and revocation. Camera and microphone controls affect their streams, not conversation history. A codec or route mismatch must be explicit before media starts.

Reuse rvoip interfaces first. If the native video experiment exposes a gap, record the upstream change or pinned patch and review the profile; do not quietly remove video or replace native QUIC with a WebSocket demo.

These video paths and targets are proposed for your review, not an assertion that the earlier feasibility decision approved all of them. Media transport does not imply that an assistant can understand video content.

Make the boundary usable by other developers.

G5-B · Connector kit

Small contracts. Complete lifecycle.

Deliver a versioned capability/configuration manifest, secret references, address validation, readiness reporting, event normalization, context provenance and recovery rules. Describe messaging and voice/media extensions separately.

Ship a template, a fixture provider and a reusable contract harness. Cover duplicate and reordered callbacks, invalid authentication, uncertain requests, cancellation, teardown and restart. Existing Vapi/Telnyx integrations remain the real-world mappings; a fixture is not a new supported provider.

Registration stays an explicit trusted composition step. No marketplace, runtime download or automatic loading of third-party code.

G5-B · Protocol kit

Prove the standard can be implemented.

Publish the exact UCTP transport profile and Connect application extensions: negotiation, authentication, envelopes, IDs, events, errors, limits and replay. Version the protocol/profile independently from the server.

Recommended independent client: a small second-language QUIC implementation built from the spec and public test vectors. It cannot delegate to the Rust helper or reuse Connect/rvoip protocol parsing. Its first proof covers reliable control and durable events; native video/media conformance has its own fixtures and path tests.

Document which rules are upstream UCTP and which are Connect-specific. Do not describe an application extension as an adopted external standard.

Reuse the current connector boundary and wire contract. The E8 readiness work provides the original extension and video exits.

Local first. Useful before any provider account.

The first successful exchange should need a download, a local identity and two participants. Provider setup is an optional second step with specific prerequisites and recoverable outcomes.

A5-08An independent UCTP client interoperates

A separately written client using a different protocol implementation reads the published profile, negotiates and authenticates over real QUIC, resolves an identity, exchanges permitted requests/events, resumes its cursor and replays one mutation safely. It must not invoke Connect’s Rust helper/client or rvoip’s UCTP implementation. Include incompatible-version, malformed-envelope and unauthorized-operation cases; use shared vectors, not shared parser code.

Milestone: G5-B · Commitments: F-17 · Qualified local technical scope · see current acceptance evidence

A5-09One honest interface matrix

Publish and execute the operation/transport matrix for Rust, Python, TypeScript, HTTP/JSON, CLI and MCP. Equivalent operations preserve authority, IDs, errors and replay semantics. Explicitly label the Python/TypeScript native helper and browser WebRTC path. Tools control sessions; they do not carry media frames. Unsupported combinations remain visible.

Remain in scope

The complete developer v0.1.

Files and video, Vapi and Telnyx, SIP and WebRTC, native QUIC, one supported additional host, both journeys, connector contribution, independent conformance and reproducible distribution.

Remain outside this gate

A small, testable product.

No hosted service, new remote deployment, consumer messenger, global directory, automatic provider fallback, multiparty video, connector marketplace or universal agent wake-up. Broader presence schedules and endpoint preferences remain B-001.

Local qualification boundary

Preserve the working system.

Use isolated state and fixtures. Keep the existing database, live provider configuration and saved credentials intact. This plan adds no remote deployment, public ingress or live provider operations to automated checks.

Historical Vapi/telephone/SMS results retain their original revisions. For unchanged routes, document the source comparison. A changed external path needing fresh provider proof remains a release blocker until a separate bounded rehearsal is authorized and recorded; simulator success cannot replace it.

Release-ready handoff

Let someone else reproduce it.

Supply install/run instructions, packages and hashes, supported versions, capability limits, protocol and connector kit, data migration/restore instructions, provenance/notices and a concise known-issues report.

Review Rust/API documentation, crate boundaries, module size and error handling as the work lands. Keep examples on public interfaces. Test clean installation outside the development workspace and publish no stronger claim than the evidence supports.
